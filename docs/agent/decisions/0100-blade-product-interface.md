# 0100 The blade_product interface

- Status: accepted (recorded by the author; the owner may reverse it)
- Date: 2026-11-01
- Decided by: Claude (agent, Opus 5.5), implementing WU6a under plan 0011, with the plan's recommended answers to its section 13 questions, which the owner's standing instruction adopts.

## Context

Plan 0011 section 2 fixes the content of `include/galoot/core/blade_product.hpp` in outline: `coefficient_type`, `detail::term`, `detail::term_list<Capacity>` with `add` in canonical order, `detail::product_capacity`, the coefficient guards, and `detail::blade_product<Capacity, N>(const metric<N>&, mask_t, mask_t)` by the direct recursion of Spike A (note 0008). This record states what the implementation chose where the plan left room, and where it departs.

## Decisions

1. Namespace. `coefficient_type` is public in `galoot::core`; everything else is in `galoot::core::detail` (decision 0015, plan 0011 departure 2). The tests use `detail`, as 0015 allows. Every declaration the tests or WU6b use carries a `///` comment with its requirements and guarantees; the two recursion helpers, `add_generator_product` and `add_blade_product`, carry `//` comments, as `blade_set.hpp` does for its internal helpers.
2. `term_list` members. The plan names a data member `size` and a member function `size()`, which cannot share a name. The count is the data member `length`, as in `blade_name`, and `size()` returns it, as in `blade_set`. The list has no default member initializers, like `blade_set`; it is value-initialized (`term_list<K>{}`), and the `///` comment says so.
3. Equality. `term` and `term_list` default `operator==`. `add` keeps every place past `size()` at `{0, 0}`, including the place a removed term vacates, so the defaulted comparison of the whole array compares sums. A test checks the vacated place, and the mutant that leaves it is killed.
4. Canonical order. `add` inserts by `canonical_less` from `blade_set.hpp`, so the header includes `blade_set.hpp` (and with it `<string_view>`) rather than restating the order. The plan names that order; a second copy of it would be a second convention to keep in step.
5. Capacity. `product_capacity(a, b)` is 2^(|A ∪ B| − 1), or 1 for two scalars, with the derivation in its comment. The derivation also bounds every partial sum formed during generation, because every term added to any list in the recursion lies on a subset of A ∪ B (of A' ∪ B for the inner product) of the right parity, and a list holds distinct blades. So `Capacity >= product_capacity(a, b)` always suffices. The requirement is checked as the lists grow, by the assertion in `add`, not at entry: a smaller capacity that suffices for the given metric gives the exact result, and one that does not fails with "more product terms than the capacity". An entry check would reject results that are exact, and the plan's rejection test (`blade_product<1, 2>` of e1 e2 in the Witt form) fails either way.
6. Value-level metric, unchecked requirements. `blade_product` takes `const metric<N>&` (Spike A finding 1), so the tests run it on metrics built at run time. It requires a symmetric form with entries within `max_form_entry`, which every factory guarantees and `metric_like` checks for a tag, and does not check this itself; the `///` comment states the requirement. An asymmetric hand-written aggregate would give a result that is not a Clifford product; reading g(i, j) transposed is an equivalent mutant on every form the requirement admits. Entries are widened to `coefficient_type` before any arithmetic, so even an entry of `INT_MIN` cannot overflow `int`.
7. Range of the masks. `blade_product` asserts that `a | b` names only e_1 to e_N, with the message `bits.hpp` uses ("blade has a generator beyond e_n"). It does not call `detail::in_algebra`, which requires 1 <= n and shifts by `mask_bits - n`; instead it shifts `a | b` right by N under `if constexpr (N < mask_bits)` and accepts every mask when N = `mask_bits`. The first version tested `N == mask_bits ||` before the shift, which GCC still diagnosed at N = 32 (`-Wshift-count-overflow` under `-Werror`); a test of R(32,0,0) found it (commits `127512d`, `5c02c3f`).
8. The recursion takes `b`, not a term list. In Spike A's form the right factor is a term list x, but every call has x = e_B, so `add_blade_product(out, g, a, b, scale)` takes the mask, and the base case adds `scale` on e_B. The wedge sign is `reorder_sign(generator, blade)` from `bits.hpp`, the count of generators of B below e_i.
9. Recursion and lint. `add_blade_product` is recursive on the grade of `a`, at most `mask_bits` deep, so `misc-no-recursion` is suppressed at its declaration with that reason. Each level holds one scratch `term_list<Capacity>`, so the stack cost at run time is about grade × Capacity × 16 bytes, which matters only for capacities far above what WU6b's plan scratch needs (inferred, not measured).
10. Rejections beyond the plan. The plan names three (`beyond_n`, `capacity`, `overflow`). Added: a compile-fail test of a sum that does not fit (`sum_overflow`), because the product overflow fails in a multiplication first and would leave the addition guard untested; and run-time aborts of a sum and a product just past either bound (`sum_above`, `sum_below`, `product_above`, `product_below`, `product_below_second`), which kill the boundary mutants of each guard.
11. The overflow input. The plan proposes "a dense form with every entry at `max_form_entry`". That form has rank one, so its pseudoscalar square, det g, is zero, and every minor of order two and above vanishes; an overflow there would rest on intermediate values, which the degree count cannot show. The test uses k I + (J − I) instead, k = `max_form_entry`, every entry nonzero: its determinant is (k − 1)^4 (k + 4), about 2^75 for k = 2^15 − 1, and the source checks from `numeric_limits` that it exceeds the largest coefficient. If no guard fired, every step would have been exact and the result would be that value, so a guard must fire. A departure from the plan's wording, not its intent.

## Consequences

- WU6b's `generate_gp` calls `blade_product<plan_capacity>` per pair; `plan_capacity` is the largest `product_capacity` over the pairs, which decision 5 shows suffices.
- `blade_product.hpp` costs every includer `blade_set.hpp`'s `<string_view>` (decision 0090's note). The umbrella header already included it, so `core.hpp` does not grow by it.
- Promotion of `blade_product` to the public interface needs no signature change (plan 0011 departure 2).
