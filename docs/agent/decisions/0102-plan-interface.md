# 0102 The interface of the geometric-product plan

- Status: accepted (recorded by the author; the owner may reverse it)
- Date: 2026-11-01
- Decided by: Claude (agent, Opus 5.5), implementing WU6b under plan 0011, with the plan's recommended answers to its section 13 questions, which the owner's standing instruction adopts.

## Context

Plan 0011 section 2 fixes the content of `include/galoot/core/plan.hpp` in outline: `detail::plan_term`, `detail::generate_gp<Capacity, N>` over two spans of oriented blades with a counting pass on an empty output, `detail::plan_capacity`, and `detail::gp_plan<Alg, A, B>`, a variable template initialized by a `consteval` function template that checks each set before generating and checks the cheap properties of the result after. This record states what the implementation chose where the plan left room, and where it departs.

## Decisions

1. Namespace. Everything in `plan.hpp` is in `galoot::core::detail` (decision 0015, plan 0011 departure 2). The tests use it, as 0015 allows. Every declaration the tests use has a `///` comment; the internal helpers (`all_in_algebra`, `plan_defects`, `defects_of`, `filled_gp`, `make_gp_plan`) have `//` comments, as `blade_set.hpp` does for its own.
2. `plan_term` is `{std::size_t a, b; mask_t out; coefficient_type coefficient;}` with defaulted `==`, 32 bytes with padding. A smaller term (32-bit positions) stays deferred (plan 0011 section 12); nothing measures the size yet.
3. Sign folding. The coefficient of a term is s_a s_b c, folded when the plan is generated, so a coefficient stored on −e14 multiplies as −e14 (CONVENTIONS 1.6) and every `out` is a canonical mask with sign +1 (decision 0091). The product of the two signs and c is not guarded: with signs ±1 it cannot leave −max to max, and a guard there would be one that cannot fire (review finding F5 of WU6a).
4. `generate_gp` requires signs of ±1 and does not check them; its `///` comment says so (C8). Its one present caller, `make_gp_plan`, checks them first with a `static_assert`, and the run-time callers are the tests. A `GALOOT_ASSERT` per blade would be cheap, but it could never fire in the compile-time path, and the run-time path has no user yet (C12). Masks beyond n and a capacity too small are checked by `blade_product`'s own assertions, which `generate_gp` reaches for every pair.
5. Output. `generate_gp` writes the first `out.size()` terms and returns the count of all, so the counting pass passes an empty span and a short span is filled without a write past its end (a test checks the places after it). Terms come in order of a, then b, then the product's canonical order.
6. `plan_capacity` is the largest `product_capacity` over the pairs, starting at 1, so that it is a valid capacity for an empty set. Decision 0100 item 5 shows that `product_capacity` of a pair suffices for every list formed while generating that pair.
7. The memoizing form is the plan's: `template <metric_like Alg, blade_set A, blade_set B> inline constexpr auto gp_plan = make_gp_plan<Alg, A, B>();` with `make_gp_plan` a `consteval` function template (note 0011). One departure in its body: every local is `static constexpr`, not `constexpr`. A Clang `-ftime-trace` of a unit with two plans showed the count and the fill evaluated when `make_gp_plan` is instantiated and then the initializer of `gp_plan` taking as long again (1.43 ms against 0.61 ms and 0.70 ms for the rigid(3) point plan; 4.51 ms against 2.09 and 2.22 ms for the line plan): Clang evaluates a plain `constexpr` local's initializer again each time the call is evaluated, so the plan was generated twice. With `static constexpr` locals, which C++23 allows in a `consteval` function, the initializer takes 21 and 26 µs. Measured over whole units (`records/performance/plan-growth/out/locals.tsv`, three repeats, spread under 0.3%), plain locals cost Clang 23.1.4 +26% of the instructions for the typed rigid(3) pairs and +43% for `full<4>` times `full<4>`, and GCC 16.2.1 nothing measurable (inferred: GCC's constexpr call cache serves the repeated call). Only `gp_plan` is emitted in an object file; the static locals of the `consteval` function are not.
8. Set checks before generation. `make_gp_plan` checks, each once per set, that every mask names only e_1 to e_n (`all_in_algebra`, on `in_algebra` of `bits.hpp`, which handles n = `mask_bits`) and that every sign is ±1 (`signs_valid` of `blade_set.hpp`, a variable template evaluated once per set and shared with `index_of`). Messages: "gp plan: a blade set names a generator beyond e_n" and "gp plan: a blade set holds a sign other than +1 or -1". Generation runs only under `if constexpr` of both, and otherwise an empty array is returned, so a misuse gives its own message and no other. The compile-fail tests forbid the messages that generation would add (`blade_product`'s range message and the checks of item 9), so the mutant that drops the guard is killed.
9. Checks after generation (V4). One pass, `defects_of`, sets five flags, each a `static_assert` with its message: a zero coefficient, an `a` at or past the first set's size, a `b` past the second's, an `out` beyond e_n, and terms out of the order a, then b, then strictly increasing canonical order of `out`. The last is beyond the plan's list: it is as cheap as the others and it also catches a repeated (a, b, out), which criterion 12 asks the tests to check. None can fire for a plan that `generate_gp` wrote; each has a mutant of the generator that fires it (the mutation record), and `defects_of` is tested directly on hand-written plans at each bound, so that a mutant of a bound is killed. Removing one of these `static_assert`s is an equivalent mutant on a correct generator, recorded as such.
10. A mask repeated within one set is not checked (decision 0092 leaves whole-set checks to the type that stores a set, WU8). Each place that lists it gets its own terms with its own sign; the `///` comments of `generate_gp` and `gp_plan` say so and a test pins it.
11. Rejections. The plan's four, and three more, each with a reason: `beyond_n` puts the stray blade last in the first set (a check of only the first blade would pass it), `beyond_n_second` puts it in the middle of the second set (the gap the WU6a review found in `blade_product`, F1), `beyond_n_31` puts e32 in R(31,0,0) (F4 of that review), and `bad_sign_second` puts a sign of 2 in the second set.
12. The overflow input. The plan proposes `gp_plan<dense5, full<5>, full<5>>`. A dense `full<5>` table does not build on Clang at the default limits (decision 0103), and the one pair shown to overflow, e12345 e12345 with det g about 2^75, is the last of the table, so which of the step limit and the guard stops the compile would depend on how far the evaluation gets before an overflow, which was not measured. The test uses the one pair e12345 times e12345 in the form k I + (J − I) of decision 0100 item 11. A departure from the plan's input, not its intent. GCC prints follow-on errors after the guard's (the count is not a constant, so the fill and the checks fail too); the guard's message comes first, and the test forbids every "gp plan:" message.
13. The signature list of the exhaustive tests moves unchanged from `blade_product_test.cpp` into `test/core/signatures.hpp`, shared by both test files, rather than being copied (commit `0c4bdb8`, listed for the review).

## Consequences

- WU7 reads `gp_plan` for the result typing and rewrites `out` as an index into the result set; nothing here depends on that step.
- A run-time caller of `generate_gp` with unchecked sets must check the signs itself; the comment says so.
- The `static constexpr` form of item 7 is the one a later generator in `plan.hpp` should follow; a plain `constexpr` local in a `consteval` initializer doubles the work on Clang.
