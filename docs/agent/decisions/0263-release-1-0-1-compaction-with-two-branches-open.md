# 0263 Release 1.0.1: the compaction runs with the documentation-tooling branches open

Date: 2026-11-21. Source: the hand-backs of plan 0045's units R6 and R7. Unit R7 wrote the release record and stopped before the run-log compaction (W8): its rerun of gate G2's open-branch check, at the matrix's records tip `6d09c0e`, found two branches beyond the one that item 3 of decision 0261 allows. Each ruling below is a reading within the plan and the owner's rulings (decision 0252); the owner can reverse any of them.

1. **The release review records are on the release branch.** `review/release-1.0.1` held 10 run-log rows the tip lacked: those of the blind review of unit R5 (`6745da5`) and of its delta review (`9f8a70f`). Both commits are cherry-picked with `-x` onto `feature/release-1.0.1` (`b8b29ca`, `9bab735`), as W7 asks and as the release record cites them. The log grew by 4 and then 6 rows, the commits' own; the open-branch check then reports 0 rows for that branch.

2. **Item 3 of decision 0261 covers the tooling branch's review branch too.** `review/docs-tooling` is the blind review of plan 0049 unit U2. It holds the rows of `feature/docs--tooling` up to the revision it reviewed and 19 of its own. Its record reaches `main` only through the tooling branch's merge, which decision 0261 holds until 1.0.1 is tagged and `main` is at T. The reasoning of that item holds unchanged: the rows are new, written after the release branch was cut, and neither branch edits a row the compaction removes. Both branches still hold the rows the compaction removes, so the union merge of the run log will bring those back at the tooling merge. Ruled, for that merge: `main` is merged into the branch first, `tools/runlog prune` is run on the branch, and `tools/runlog check` must then report every era matching, each kept row present once and no removed row present. The same applies to any later fix round or delta review of U2 that opens a branch before the tag.

3. **The compaction's revision.** The compaction runs at the tip of `feature/release-1.0.1` after this decision and the cost rows are committed, so that the new era covers the matrix, the seed campaign's rows, the release reviews and the closing gates before it. The plan's phrase "the matrix's records tip" is read as the release branch's records tip at the time of the compaction; no commit since the matrix changes anything outside `docs/agent/`.

4. **Two cost questions are closed for this release** (the matrix record's open items 1 and 2). The growth of a build row outside its compile rows, seen once at `41d8029` (plan 0044's open item 4), did not repeat at R and is closed as a single sample. The sanitizer presets' rise after the test splits reproduces from a second empty tree (gcc-asan 11,727.7 G against 11,722.3 G) and is recorded as a stable cost of the split sources, cause untraced; a time report of one law source against the old unit goes to the next cost pass.

5. **Wall time of `clang-measure-o3`.** The release record quotes the cost-cleanup matrix's 127.6 s with the release matrix's instruction count, because the release matrix's 213.5 s overlapped the tooling unit's lint build. The tree is not rebuilt for a figure (P10).

6. **Two record corrections, neither voiding R.** The header of `records/diagnostics/catalogue/scan-output.md` names Clang 23.1.4; the trees it was generated from were configured after 23.1.5 was installed. It gets a dated one-line correction in the continuation of R7. `tests.citations` does not read `CHANGELOG.md`; the file is added to the test's paths in the first unit after 1.0.1 that changes `test/CMakeLists.txt`. For this release the citation tool was run over the file by hand, by three agents, with no finding.

7. **A wording nit kept.** The delta review notes that the changelog's build bullet says "the presets" where the documentation bullet says "build presets". It stays as written: an edit would make a new release commit and rerun the matrix.
