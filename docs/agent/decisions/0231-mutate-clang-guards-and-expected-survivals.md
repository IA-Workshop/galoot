## Context

1. **Clang's guard.** GCC reports a guard such as `GALOOT_ASSERT` that stops constant evaluation as "call to non-constexpr function", at the call; decision 0214 item 5 classes that `assert`, wherever it lies. Clang reports the same failure as an error about the constant expression that stopped, at the place that asked for it: in a test, "constexpr variable 'accepted' must be initialized by a constant expression", which the driver classed `test`, a kill; in a `static constexpr` variable of a library header, the same error in the header, which it classed `invalid`. The call is named only in a note: "non-constexpr function 'assertion_failed' cannot be used in a constant expression". So the WU12 blind review's mutants `image_capacity_full_grade` and `lcm_as_product` were killed on GCC and unjudged on Clang (finding N6, `records/reviews/2026-11-09-wu12-blind-review.md`).
2. **Expected survivals.** A spec could expect only `killed` or `equivalent`. W3 judges a gap's mutant by its survival against the suite before the gap's tests, and the units since (plans 0030 and 0032, and the blind review of plan 0032) ran such specs with `expect = "killed"` and read the exit status of 1 as the expected result by hand. The same holds for a form that one compiler compiles correctly and the other does not.

## Decision

1. **Class `assert`** also covers an object's first error whose notes, the lines after it up to the object's next error or the end of its output, include Clang's "non-constexpr function '…' cannot be used in a constant expression". Clang writes that note when a constant evaluation stopped at such a call, whatever the error that asked for the constant: a constexpr variable, a `consteval` call, a `constinit` variable, an `alignas` argument. The location stays the error's own line, so the killer named for a Clang build is the variable that asked for the constant, not the call. A constant evaluation stopped by anything else (an overflow, a read outside an object's lifetime) keeps its old class, `test` in a test file, else `invalid`, on both compilers, also when a guard fails after it in the same object.
   - Known limit: a guard inside a `consteval` function called from a header, outside a constant context. Clang's first error, "call to consteval function '…' is not a constant expression", carries the note and is now `assert`. GCC's first error is the same call; the call to the function that is not constexpr follows as a second error, which the class does not read, so GCC's object stays `invalid` and the mutant unjudged. Before this change both were unjudged. A spec that meets the case reads the Clang row, or a later unit extends the GCC rule to read that second error.
   - Known limit of the same shape: a guard reached from a `constinit` variable of a header. Clang's first error ("variable does not have a constant initializer") carries the note and is `assert`; GCC's first error ("'constinit' variable '…' does not have a constant initializer") does not name the call, which follows as a second error, so GCC stays `invalid`. In a test file both compilers kill. Neither `include/` nor `test/` uses `constinit` at present.
   - Known limit, shared with GCC's rule of decision 0214 item 5: a mutant that calls a function that is not constexpr on a compile-time path, or drops `constexpr` from one, is `assert` (a kill) on both compilers, though no check of the library failed.
2. **`expect = "survived"`** declares that the selection is expected to let the mutant live. It needs a `reason`, as `equivalent` does, and is refused with `killers`. A survivor so declared is no problem; a kill is, as "expected to survive but killed"; an unjudged mutant is a problem as before. The verdicts themselves are unchanged: such a mutant is still reported `survived`, and its `expected` cell says `survived`.

## Options weighed

- For item 1: match the note's function name, `assertion_failed` (the WU12 review's suggestion), which ties a general tool to one library's spelling and misses the tests' fixtures and any other guard; or class every Clang constant-expression error `assert`, which would count an overflow in a library's table, a defect of the mutant rather than a check, as a kill on Clang and not on GCC. The chosen rule is the Clang counterpart of the GCC rule decision 0214 already uses, so the two compilers agree on the fixture's four cases (the guard reached from a test, from a header's variable, an overflow there, and an overflow there followed by a guard). The first draft also asked that the error's text hold "constant expression". It was dropped: no test judged it, and keeping it would only trade one disagreement for another, since the `alignas` case then stays `invalid` on Clang while GCC, whose first error there is the call itself, already classes it `assert`; without it the `constinit` case disagrees instead (see the known limits).
- For item 1's location: the note's line, which would name the same killer on both compilers. Not chosen: the class is read from the first error line, and moving the location to a note would make the killer of a Clang build depend on which note is read first; the rows of existing specs would also change.
- For item 2: a second spec expecting `killed` read by hand (the practice so far), or a per-preset `expect` table. The table is not needed by any record yet; a unit that needs it adds it.

## Consequences

- A Clang row that was `test` for a guard reached from a test is now `assert`, at the same line and with the same killer (`tools.mutate`'s `guard_kill`). Its verdict is unchanged. A Clang row that was `invalid` for a guard in a header is now `assert`, and its mutant is killed.
- The records that read a Clang survival or an unjudged Clang guard by hand stay as written; a later run of their specs may show the new verdicts.
