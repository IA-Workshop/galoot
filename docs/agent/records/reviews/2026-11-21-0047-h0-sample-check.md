## Sampled rows

For each row: my own result, then how it compares with the register.

### Medium rows

**A03, `GALOOT_CHECKING` mixed across units.** My result: `checking_now()` (`assert.hpp:115-120`) is an inline function whose body reads the macro, so a 0 in one unit and a 1 in another give two different definitions of one inline function. That breaks the one-definition rule: the program is ill-formed, and no diagnostic is required. Reproducer: a checked unit and an unchecked unit each call `antigrade(0x80, 3)`, which breaks its precondition, and are linked in both orders. At `-O0`, on both compilers, the checked unit's call aborts with the message when the checked object is linked first, and returns 2 unchecked when the unchecked object is first. At `-O2` both orders abort, because each unit inlines its own copy. Nothing in the guide forbids mixing the modes (`core.md:970-981`, `:1442-1447`), and `assert.hpp` states the rule only for `GALOOT_FORCE_INLINE`. So checks vanish silently, by link order, from a configuration nobody forbids. **Agree**: confirmed, medium, and the register's effect statement is right.

**A09, a name list in a `char` array without a final null.** My result: `name_list::text()` (`blade_set.hpp:400-402`) always returns `L - 1` characters. With `inline constexpr char raw[] = {'e','1','2'};`, `blades<pga3, raw>` compiles on both compilers and holds one blade, mask 1 (e1). `{'e','1',' ','e','2','3'}` gives e1 and e2. No diagnostic appears in any mode, and the wrong layout then shapes every value of the type. **Agree**: confirmed, medium.

**A21, term-list capacity at 22 generators.** My result: for an antiproduct of two vectors in n generators, the complements' union holds all n generators, so `product_capacity` (`blade_product.hpp:186-192`) asks for a `term_list` of 2^(n-1) terms. Clang refuses a constant-evaluated array whose bound exceeds its step limit (2^20 by default). So I predicted the first refusal at n = 22, before running anything. Reproducer: `geometric_antiproduct` of two `e1 e2` vectors in `R<n, 0, 0, 32>` over double. Clang builds at 21 and refuses at 22 with "cannot allocate array; evaluated array bound 2097152 exceeds the limit (1048576)". GCC builds both. **Agree**: confirmed, medium. On the severity: the scale puts "a valid input refused" under low and "a documented bound that fails for an accepted input" under medium, and this row is both. Medium is the right reading because the refused input is sparse, two blades of two generators. That contradicts both `metric.hpp:51-55` ("every later part of the library accepts") and the guide's "a sparse layout costs what it uses" (`limits.md:28-31`). I compared it with A24 (low): there, dense vector layouts reach the placement cost that `limits.md` documents. The two ratings are consistent.

**A22, the float16 rounding check.** My result: `std::float16_t` meets `rounding_checked_scalar` (`is_iec559`, round to nearest), and the margin holds for K up to 31, so the type is checked. The padding is τ = λ/u = 2^-14 / 2^-11 = 1/8. Each tolerance therefore has a floor of about γ_(K+1) · W · τ ≈ K · W · λ. Reproducer, on GCC, since Clang with libstdc++ has no `std::float16_t`: the header's own non-versor from R(4,0,0), v = s(1 + e12 + 2 e13 + 3 e14) acting on x = s e1, in checking mode at run time. The dropped part is 2s³ on three blades and the floor is about 5×10^-4. The check aborts for s ≥ 0.05. At s = 0.03 it passes: the dropped coefficients are 5.4×10^-5, 1.1×10^-4 and 1.6×10^-4, while the kept e1 coefficient is 3.5×10^-4. So a gross non-versor passes once inputs are a few hundredths, and the documentation (`transform.hpp:713-728`) states the floor only for double and float. **Agree**: confirmed, medium. One wording point, minor finding M1.

**A36, narrow unsigned scalars.** My result: in `run_product` (`mv.hpp:366`), `x[a] * y[b]` for `std::uint16_t` promotes both operands to `int`, and 65535 · 65535 exceeds `INT_MAX`. That is signed overflow, which is undefined, even though `mv.hpp:745-748` calls unsigned arithmetic modular. Reproducer: (65535 e1)(65535 e1) in R(2,0,0). UBSan on both compilers reports "signed integer overflow: 65535 * 65535 cannot be represented in type 'int'" at `mv.hpp:366`. The unoptimized result is the modular 1, and a constant evaluation is rejected on both compilers. **Agree**: confirmed, medium. Reading the evidence afterward: the register also extends the row to `mv.hpp:313`, the scaled-term path, with its own reproducer `merge/m01`. I did not rerun that part.

### Other confirmed rows

**A05, `bits.hpp` with n outside 1 to 32, unchecked.** My result, with `GALOOT_CHECKING=0` and UBSan: `complement_mask(1, 0)` reaches `low_bits(0)` = `~0u >> 32`, and UBSan reports a shift exponent of 32 at `bits.hpp:50` on both compilers. `antigrade(0b111, 2)` returns −1 and `antigrade(0, 40)` returns 40. These are broken stated preconditions in an unchecked build. **Agree**: confirmed, low.

**A06, `canonical_name` beyond e9, unchecked.** My result: the loop stops at bit 8, so e10 gives "e" (length 1), and e1 e10 gives "e1", a plausible but wrong name. **Agree**: confirmed, low. The register states only the first effect; minor finding M2.

**A16, a change of basis refused for the elimination's overflow alone.** My result: Bareiss's step forms `a_kk a_ij − a_ik a_kj`, a product of two k-minors, before dividing by the previous pivot. The intermediate value can therefore reach about ‖row‖^(2k) while every minor, inner product and inverse entry fits. Reproducer: the orthogonal R(4,0,0) change from the quaternion matrix of (1500, 900, 740, 519), with each row over 1969 (1500² + 900² + 740² + 519² = 1969²). Its inverse is Pᵀ/1969, its inner products are 1969², and its determinant 1969⁴ ≈ 2^43.8 fits. An exact Python transcription of the elimination predicted an intermediate product of 2^76.2. Both compilers refuse the change at `basis_change.hpp:719` with "an exact value the change computes does not fit coefficient_type". The same matrix shape built from (1, 2, 2, 4) over 5 is accepted. **Agree**: confirmed, low (a valid input refused, with a message). Reading the evidence afterward: the register's own smallest case, R(3,0,0) from (79, 2, 1, 1), is consistent with this.

**A23, an integer scalar's own overflow.** My result: over `int`, (46341 e1)² gives −2147479015, and UBSan reports signed overflow at `mv.hpp:366`. Over `std::int16_t`, (200 e1)² gives −25536, because the operands promote to `int` and the result is converted back, so it wraps silently. Meanwhile `mv.hpp:892-895`, `transform.hpp:764` and `basis_change.hpp:1136-1137` say that "with an exact scalar the result is exact". **Agree**: confirmed, low. The overflow belongs to the scalar's own arithmetic, and that is what separates this row from A36's medium: there, the library's promotion makes undefined an arithmetic that is defined as modular.

**A37, `rotation` with subnormal squares.** My result: at |v| ≈ 2×10^-160 the squares are subnormal, the computed length loses relative accuracy, and the check still passes, because a square root is never subnormal. The rotor's weight norm minus 1 is 2.2×10^-16 at 2.2×10^-155, 1.3×10^-6 at 2.2×10^-160 and 3.35×10^-160, and 2.3×10^-4 at 2.2×10^-161. Lines 36-37 ("a direction of any positive length") contradict lines 52-54 (the length must be at least about 1e-150). **Agree**: confirmed, low. Its evidence, "7.5e13 u at length 1e-161" (about 8×10^-3), is a different input than mine and of plausible size.

**A38, an overflowing product coefficient.** My result: a diagonal form of five entries 32767 (each within `max_form_entry`) with e12345 · e12345 = 32767⁵ ≈ 2^75. Clang emits **3** errors ("3 errors generated.") and GCC emits **13**. The library's message appears in an echoed source line on both. On the register's own case (`numerical/p05_coefficient_edges.cpp`, `-DCASE=4`), rerun at this commit, the counts are again 3 on Clang and 13 on GCC. **Disagree on the value**: the register's condition ("4 errors (Clang) or 14 (GCC)"), its ranking table ("4 to 14 errors") and N07 ("Clang reports four errors") are each one too high. `numerical/run.sh:36` prints `grep -c 'error'`, a count of lines. On Clang that takes in the summary line "3 errors generated."; on GCC, the note "substitution of deduced template arguments resulted in errors seen above". The verdict (confirmed) and severity (low) stand. Finding E1.

**A41, the rationale of `max_form_entry`.** My result: every arithmetic use of a Gram entry is in `coefficient_type` (`blade_product.hpp:219`, `:254`; `basis_change.hpp:546`, `:564`). No 2×2 minor is ever formed in `entry_type`, so the sentence at `metric.hpp:57-60` and `limits.md:110-113` gives a reason the code does not use. **Agree**: confirmed, nit.

### Dismissed rows

**A14, negating the least `coefficient_type`.** My result: every value that reaches `x < 0 ? -x : x` (`blade_product.hpp:91-92`, `basis_change.hpp:266-267`, `:315-316`) is one of three things: a Gram entry (|g| ≤ 32767), a row entry widened from `int`, or the output of `add_checked`, `multiply_checked`, `add_noting` or `multiply_noting`, which keep values in [−max, max]. The quotient in `eliminate_entries` cannot leave that range, and the unchecked `sign *` at `basis_change.hpp:520` multiplies such a value by ±1. So `INT64_MIN` is never formed, and these functions run only in constant evaluation, where undefined behavior would fail to compile anyway. **Agree**: dismissed.

**A27, the formatter's buffers.** My result: a printed name is at most "-", "e" and nine digits, 11 characters, which is the size of `printed_name::chars`. Declared names pass the same parser, so they are at most 10 characters. The names are built in a `consteval` function, where an overrun would fail to compile. Above nine generators the formatter is rejected by `static_assert` (`format.hpp:220-224`), and the run-time `write` only copies those fixed names. **Agree**: dismissed.

**A34, integer division by zero and `min() / -1`.** My result: for an integer T, `operator/` checks `s != T{}` with `GALOOT_ASSERT`. The declaration (`linear.hpp:383-411`) says that the division by zero is undefined with checking off, and that `min() / -1` is the scalar's own overflow. Its claim that short and signed char give `min()` again is right under C++20's modular conversion. The text is accurate, so nothing undocumented happens. **Agree that nothing is wrong**, but the classification is not consistent with the register's own scale; minor finding M3.

**A43, the margin inequality.** My own derivation: γ_(K+1) / γ_K ≥ (1 − u)^−(2K+1) follows, through Bernoulli's inequality (1 − u)^(2K+1) ≥ 1 − (2K+1)u, from 1 − (K+1)(2K+1)u + K(K+1)(2K+1)u² ≥ 0. That holds whenever (K+1)(2K+1)u < 1. I checked (1 − u)^(2K+1) γ_(K+1) ≥ γ_K exactly in rationals for every admitted K for binary16 (K ≤ 31) and binary32 (K ≤ 2895), and for K = 1, 10, 100 and 1000 for binary64. Margin 0 fails at the largest K of each type. The rest of the derivation at `transform.hpp:457-480` holds when I read it step by step:
- fl(γ_k) ≥ (1 − u)γ_k, because k·u and 1 − k·u are exact;
- each padded product is at least (1 − u)²(z + τ) when τ ≥ λ;
- rounding to nearest is monotone.

**Agree**: dismissed.

**`rga3/motions.hpp`.** Registered sites:
- `rotation`'s angle (A18);
- subnormal squares (A37);
- `translation` over `bool` (A19);
- `translation` without division (A40);
- the rotation bound (A48, open).

I checked the remaining arithmetic against its comments, and each claim holds:
- the stated cost of nine multiplications and two additions;
- "a square root is never subnormal";
- exact halves in `translation` except for subnormal components;
- that a far line's moment times sin/length cannot overflow unless its distance from the origin exceeds the largest double.

**One site the register lacks** (minor finding M4): `rotation`'s precondition that l is a line, v · m = 0 (`motions.hpp:49-52`). It is stated, unchecked in every mode, and has no row in either read or in the merged register. Its documented effect is a motor that "distorts what it moves". A join computed in floating point meets it only up to rounding, so a check would need a tolerance. That is a rounding-edge question for H3, of the same kind as A18.

## Open items for the coordinator and the owner

1. **Whether E1 is "an error" under decision 0253 item 12.** That item moves H0 and V3 to the Fable level "if a sample check finds an error". Under this brief's definition E1 is an error, a wrong value in a sampled row. The options:
   - (a) Treat E1 as the trigger and redo H0 at the Fable level. This costs the most and addresses something a model change does not fix: the cause is a counting command in three scripts, not a judgment.
   - (b) Correct the counts and the scripts in H0's branch, with a delta check of the corrected rows, and keep the Opus level. This is cheap and fixes the cause.
   - (c) Correct the counts and also widen the sample on the rows whose effect is a count or a threshold (A19, A24, A25, A31, A38, A39) before H1 starts. This costs a little more than (b) and protects H1, which pins counts.

   Recommendation: (c). It fixes the systematic cause and checks its reach, and no sampled verdict or severity was wrong. Whether item 12's trigger is met, read literally, is the owner's to decide, so I flag it rather than settle it.
2. **M3's rule for documented behavior.** Options: (a) dismissed when documented and pinned by a test; (b) always confirmed, as "documented". (a) keeps the confirmed list to things that need work, while (b) keeps every behavior that surprises a user in view. Recommendation: (a), with the test named in the row.
3. **A knowledge-base note** (not written; outside this brief's scope): "Counting compiler errors: `grep -c error` counts lines, and Clang's 'N errors generated' and GCC's 'errors seen above' each add one". Recommendation: add it in the next unit that may write to the knowledge base.
