## Shell traps

I read each line under `set -euo pipefail`.

- **Negated commands and pipelines.** There is no `! cmd`. The two `if cmd; then fail; fi` lines are right (the draft's note says why). `git show | awk ... || fail` works: `pipefail` makes a missing log, or a failing `awk`, stop through `fail`. In the loop (line 51) the same pipeline sits inside `n=$(...)`; there a missing log would stop the script through `set -e`, silently, with git's own `fatal:` line as the only message. Harmless, because the line above it already read the same file.
- **`[ "$(a)" = "$(b)" ] || fail`.** A failing `git rev-parse` inside the substitution gives an empty string and a mismatch, so the check fails with its message, as intended (the `tag missing` and `master missing` runs).
- **Quoting.** Every expansion is quoted. `"$T^"` and `"$PREV^{commit}"` expand correctly. `awk -v` is given strings without backslashes.
- **Patterns.** `grep -qF` is fixed-string, so the dots in `1.0.1` cannot match other characters. The two real looseness cases are F6 (substring match of the CHANGELOG heading) and F2 (any `check` row). `':!docs/agent'` matches only paths under that directory (a path `docs/agentx` would not match). `--short=12` matches the log's 12-character column; a longer abbreviation would need ambiguity, which `git rev-parse --short=12` resolves by lengthening, and then the row would not match; this stops the script safely and has not happened.
- **Files read at step 2** are the working tree's, not `main`'s. With a clean tree on `main` they are the same.
- **No `--` before the revisions** in `git diff main master --stat` and `git diff master master^2`. A file named `main` or `master` in the repository root would make git refuse; none exists.
- **`--dry-run` handling** is the one real trap: F1.

## Findings

Most severe first. None is blocking. "Smallest fix" is a change to the script; I did not make any.

### F1 (major). Any argument but exactly `--dry-run` runs the real release

Line 63: `if [ "${1:-}" = "--dry-run" ]; then ... exit 0; fi`. Anything else, including `--dryrun`, `--dry_run`, `-n` and `--help`, and also `--dry-run` as a second argument, falls through to step 5. Confirmed: in the scratch clone, `script.sh --dryrun` merged `master` and tagged `1.0.1`; `--help` did the same; `--dry-run extra` stopped (only the first argument counts). The brief's hard rule for agents, and the plan's walkthrough (O8), both rest on the dry run being a safe command. The 1.0.0 script had the same line.

Smallest fix, after line 22:

```bash
case "${1:-}" in ""|--dry-run) ;; *) fail "usage: close-out-1.0.1.sh [--dry-run]" ;; esac
```

### F2 (minor). Step 3 accepts any passing `check` row, not `tools/runlog check`'s

Lines 50 to 53 test column 4 (`check`, `trace`) and column 8 only. T's parent has four such rows: `gate:runlog` (the `tools/runlog check`), `gate:trace`, `gate:citations` (exit 1) and `gate:citations-code-paths`. Confirmed: with `gate:runlog@334ec44` set to exit 1 and `gate:citations-code-paths@334ec44` left at 0, the dry run passes. The same would pass if `gate:runlog` were absent. Both gates did pass in the real log, so nothing is wrong today. The release record's rule 2 ("`tools/runlog check` and the trace gate passed") is not what the script tests.

Smallest fix: also match the selection, in column 6:

```bash
for sel in runlog trace; do
  n=$(git show "$T:$RUNS" | awk -F'\t' -v c="$P" -v s="gate:$sel@" '$2 == c && index($6, s) == 1 && $8 == 0' | wc -l)
  [ "$n" -ge 1 ] || fail "no passing gate:$sel row at $P"
done
```

### F3 (major). The script never compares the code on `main` with R

Step 1 anchors on T. The only link between the matrix and the code is the string `gate:all@578aa15` in the selection column (column 6); column 2 (the revision, `f6e00fb962bc` for all 33 rows) is not read. A commit between R and T that changes `include/`, `test/`, `tools/`, the README or the changelog would pass every step, and the tag would carry code the matrix did not test. Plan 0045 R9 and the release record's rule 3 say such a commit voids R. Today it is true that nothing outside `docs/agent/` changed after R (the table above). The same gap existed in the 1.0.0 script.

Smallest fix, in step 1:

```bash
git merge-base --is-ancestor "$R" main || fail "main does not hold R"
[ -z "$(git diff --stat "$R" main -- . ':!docs/agent')" ] || fail "non-records change after R"
```

The second line implies the existing one for T (T is between R and `main`), so it can replace line 29. It also keeps the 1.0.0 check that nothing outside `docs/agent/` changed after T.

### F4 (minor). Step 5 leaves no recovery advice, and the dry run cannot see two of its preconditions

Step 5 is three commands that change state, then a check, then another command that changes state. A stop between any two leaves `galoot-master` or a moved `master`, and a rerun then stops at step 4, saying "exists" or "master moved". The owner is left to work out which state they are in. The table "Step 5 stopped midway" gives the commands; they could be printed. Also: the dry run passes when `master` is checked out in another worktree (the real run then stops at `git worktree add` with nothing changed, which is safe) and when `galoot-master` is a dangling symlink (`[ ! -e ]` is true for one).

Smallest fix: a `trap` that, on a nonzero exit after line 65, prints the recovery lines of the table, and one more check before line 63:

```bash
if git worktree list --porcelain | grep -qx 'branch refs/heads/master'; then fail "master is checked out in a worktree"; fi
[ ! -e "$W" ] && [ ! -L "$W" ] || fail "$W exists"
```

### F5 (minor). The `origin` check reads the fetch URL; the push uses the push URL

Line 39 uses `git remote get-url origin`. A `remote.origin.pushurl` (or an `url.<base>.pushInsteadOf`) pointing elsewhere would pass, and the printed `git push origin ...` would send `main`, `master` and the tag there. In the real repository both URLs are the GitHub one (`git remote -v`, and no `remote.origin.pushurl` or `url.*` setting). Confirmed in the scratch clone with `git remote set-url --push`. Smallest fix: also test `git remote get-url --push origin`.

### F6 (minor). The CHANGELOG pattern matches more than a level-2 heading

Line 38: `grep -qF "## $V " CHANGELOG.md` finds the text anywhere in a line, so `### 1.0.1 (...)` and `foo ## 1.0.1 bar` pass. Confirmed with `### 1.0.1 (`. It does not match `## 1.0.10 ` (the space), and it does not check the date. Smallest fix: `grep -q "^## $V " CHANGELOG.md` (the dots are then regular-expression wildcards that can only match more dots or other characters in the same place; use `grep -q "^## ${V//./\\.} "` if that matters).

### F7 (note). The printed push is not atomic

If the remote's `main` had moved (the script never fetches, so it cannot know), git would reject `main` and still push `master` and the tag. Smallest fix: `git push --atomic origin main master $PREV $V`. Today the remote's `main` is the `c95fee51` that the clone knows, so it is a fast-forward (my `ls-remote`, departure 5).

### F8 (note). The merge prints about 1,600 lines of diffstat and file-mode lines before the "done" lines

Seen in the scratch run. The owner must scroll to the end for the push lines, which are the last three lines. `git merge --no-ff --no-stat` removes the noise.

### F9 (note). What the script does not check, which I checked by hand

(a) That T adds only run-log rows (release record rule 2): `git show --stat 75b9a030` is one file, 4 insertions. (b) That each preset has its three rows (the count is 33, not 11 times 3): all eleven have one `configure`, `build` and `test` row. (c) That the script file itself is the reviewed one: step 1 allows any records change after T, and the script is a record, so this file or the review's cherry-pick can change after my review. Before running it, the owner can check that `git rev-parse main:docs/agent/records/release/close-out-1.0.1.sh` still prints `e962b0f9ea5283b5ef9af1cec0cd0911776b4248` (or read the diff since `1655ef33`).

### F10 (note). A concurrent change to `main` during the run

There is no lock. A fast-forward of `main` by another session between step 1 and the merge would merge the later tip. The window is under a second (a full run took 0.6 s). The owner should have no agent session merging at that time; nothing in the script can enforce it.
