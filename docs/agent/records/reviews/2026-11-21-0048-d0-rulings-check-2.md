## Findings

1. **Error of fact, README: the pointers and the text they point to do not wait for the same condition.**
   - **What the README says.** It states that pointed-to text "waits for the same condition as the comment that points to it, so a reader never follows a pointer to text that is gone" (README line 96). It also says that `transform`'s pointer (`transform.hpp:752-754`) and `:590-610` "wait for D3 and the S11 amendment together, so the pointer becomes one to the diagnostics heading when both go" (line 390).
   - **What the table does.**
     - The pointer at `:752-754` is in row `751-763`: a delete to limits 'The rounding check' that waits for "the S11 amendment" alone. `:590-610` waits for D3 and the S11 amendment. So the pointer is deleted, not rewritten, and it may go first.
     - `change_basis`'s pointer row `basis_change.hpp:1113-1116` waits for D3 and the S11 amendment, while `:51-65`, the list of factors it points to, waits for the amendment alone.
     - Only `bulk`'s pair (`dual.hpp:368-376`, `:44-59`) waits for the same condition.
   - **Failure scenario (plausible).**
     1. The no-drift checks pass once every reference entry exists, so the amendment applies.
     2. `concepts/metric-and-signature.md`, the target of `:1113-1116`, has not yet passed review, so D3 is not met for that row.
     3. A comment unit may then delete `basis_change.hpp:51-65`, while `change_basis`'s comment still says that the header's comment lists the operations it preserves "with their factors".
   - **Second consequence.** A unit that acts on `transform.hpp:751-763` is told by the row to delete and by the README to rewrite the pointer.
   - **Blocks:** does not block a merge of records. It should be corrected before any comment unit uses the table.
2. **Error of fact, two notes give a neighbor's old condition.**
   - `unary.hpp:18-24`'s note says the sentence that `25-27` moves "waits for D3". `transform.hpp:589`'s note says "(590-610, which waits for D3)". Both neighbors now wait for D3 and the S11 amendment, as the regenerated boundary report shows.
   - The rewrite instruction in each note still holds, so no verdict is affected.
   - Also, from before these commits: `basis_change.hpp:1113-1116`'s note says "the header's prologue list moves there", but `:51-65`, the list, is a delete to core 'Change of basis', and only `:66-82` move to the concepts page.
   - Minor.
3. **Plausible: three early rows that may be the only header statement of a guarantee.** Each is a judgment against the README's definition, and the README explicitly cleared the first two.
   - `transform.hpp:41-46` (delete, nothing to wait for, 6 lines).
     - **Text.** λ^(k-1) T(a1 ∧ ... ∧ ak) = T(a1) ∧ ... ∧ T(ak). This is what `transform` preserves, in any algebra. No other header line states it in general.
     - **Elsewhere in the headers.** `objects.hpp:84-86` and `:97-99` state it for rga3 motors and flectors only. The note of `:84-86` gives "transform and compose state it in transform.hpp" as the reason, and once `:41-46` goes, `transform.hpp` does not.
     - **The README's reason.** "a consequence of the formula `transform`'s comment keeps". That would clear `basis_change.hpp:51-65` as well, which the README holds.
   - `plan.hpp:47-56` (move, D3, 10 lines). Under a scalar in which an integer such as 2 can vanish, a result layout may hold a blade that is always zero. The public layout comments say "the blades the product can reach", and the row's own note says core 'Result layouts' lacks the caveat. The README classes the block as an explanation of why a guarantee holds, but the caveat is a limit on the guarantee, stated only here.
   - `presets/rga3/motions.hpp:17-18` (delete, nothing to wait for). The text is "rotation is found from any namespace by argument-dependent lookup". It is the only header statement of that, since `rotation`'s comment does not say it. The README holds lookup caveats because the same kind of text on a declaration is public contract, and `part`'s comment (`mv.hpp:1097-1098`), a public contract row, states its lookup in the same way.
   - If all three were held: the stage before D3 becomes 2,682, and the stage after D3 becomes 2,571. The end state is unchanged.
   - Minor.
4. **Wording: "contract text, in the sense below" covers rows the README says are not contract text.** The waiting table says that rows waiting for D3 and the S11 amendment are "contract text, in the sense below" and that no D1 or D3 row holds any. But the README itself exempts `dual.hpp:44-59` ("not contracts in this sense ... held back only because `bulk`'s comment points to it"), and `transform.hpp:590-610` is held for the same reason. Better: name the pointer rule as a second reason to wait, beside contract text. Minor.
