## The two owner-level claims

**(a) The 4.4 wording.** The ratified O2 sentence, "Either way the transform is the outermorphism of V's action on vectors", is false in general, for two separate reasons:

- **The scale factor.** T(1) = λ, but every outermorphism maps 1 to 1. At grade k, T = λ M_∧, while the outermorphism of the vector map λM is λ^k M_∧. So the sentence holds only when λ = 1. My samples show the λ^(k−1) relation at every grade in eight forms.
- **The hypothesis.** Without (H) the sentence fails even when V ⟇ V̰ = λ𝟙. In R(6,0,0), V = 1 + 𝟙 has V ⟇ V̰ = 2𝟙, but T(e1) = −2 e23456 (I recomputed this).

The committed sentence (CONVENTIONS.md:60) is correct as far as I can check. It names the factor, restricts to antiproducts of hyperplanes, and keeps the λ = 1 reading for unitized motors and flectors. It changes no value. It corrects a false sentence rather than weakening a true one, and I recommend that the owner confirm it. It is still unratified text in a document whose status line says it is ratified (finding 1).

**(b) R10 and the hypothesis (H).** Plan 0021 R10 claims the result "for every n and every form where V ⟇ V̰ is a nonzero multiple of 𝟙". That is false, by the same R(6,0,0) example: V has one parity (antigrades 6 and 0) and λ = 2, yet a vector maps to grade 5. The example is a known published one. The knowledge base gives it as the n = 6 counterexample 1 + e1…e6 (Gallier, arXiv:0805.0311, remark after Cor. 1.12, citing Porteous, Prop. 13.58), with the shortcut that works up to five generators for nondegenerate forms. Under (H), theorem 4's proof reads correct to me, and my samples agree. (H) is automatic for n ≤ 4 by lemma 5.1, which I checked. For n = 5, decision 0177 claims (H) is automatic when the form has rank at least 2, degenerate forms included. That is stronger than the knowledge base's nondegenerate statement. I read the proof and found no gap, but I did not test it with samples.

## Usability checklist

**Tasks, written from the examples before reading the header:**

1. Move a point by a turn followed by a translation, as one motor.
2. Reflect a point or a plane in a mirror plane.
3. Make the plane through a point that is parallel to a given plane.

The header example and the antiproject comment cover all three. I read the implementation for one thing only: whether `transform` checks that V is a versor. It does not, it checks only the dropped part, and the comment says so.

**Names**

- [x] The names are the field's terms: `compose`, `transform`, `antiproject`, and `compose_layout` and `antiproject_layout`, which follow the existing `*_layout` names.
- [x] One meaning across the library. `transform` clashes with `std::ranges::transform` under `using namespace std::ranges`, and the header documents this at lines 58-63.
- [x] Similar things look alike. `antiproject(a, b)` mirrors `project(a, b)`, object first. `transform(x, V)` puts the object first and `compose(Q2, Q1)` uses the mathematical order, both as CONVENTIONS 4.4 has them.

**Construction and conversion**

- [x] No new constructors.
- [x] The result of `compose` is canonical and converts explicitly (`Motor{compose(q2, q1)}`).
- [x] There is no hidden default.

**Misuse and diagnostics**

- [x] Each item of the catalogue has a compile-fail test on both compilers, requiring the literal message, also in the form `auto r = ...;`, with the internal names forbidden on the first error line.
- [x] Distinct causes give distinct messages.
- [x] The probes are documented: a requires-expression is told yes.
- [ ] The run-time message does not give its fix (finding 5).

**Semantics and cost**

- [x] The `///` comments state what is dropped and checked, that `transform` does not unitize, the result layouts, and the compile limits.
- [x] `auto r = transform(p, m);` is safe: the results are values.
- [x] Comparisons are exact.

**Examples and readability**

- [x] The example is the idiom to copy.
- [ ] Its double result is printed as if it were exact (finding 6).

**Before release.** I suggest no interface change that would break users later. The one to settle before release is the message text of finding 5, since users may match on it.
