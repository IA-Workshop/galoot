## 5. Findings, most severe first

None blocks the merge.

### F1. The zero-divisor check is pinned for one type and one sign. Its comment has three gaps. Minor; does not block (tests and comment; cheap).

`include/galoot/core/linear.hpp:351-365`; `test/core/linear_divide_*`, `linear_test.cpp:620-649`.

- Every test of the check divides a `std::int64_t` line by 0 or by 2. Two wrong checks pass the suite (section 4): one that aborts on every negative divisor, and one that skips unsigned types, where `x / 0u` is undefined. Scenario: a later edit to `s > T{}` makes `line / std::int64_t{-1}` abort in every checking build and fail every constant evaluation, and no test notices. Fix: add `static_assert`s that divide by −2 over `std::int64_t` and by 2 over `unsigned` and `short`, and constant-evaluation probes (a concept like `parts_in_a_constant_evaluation`) showing that `x / 0u` and `x / short{0}` are not constant expressions. My probes 8 and 9 show both fail on both compilers on the branch as written.
- "A floating T is not checked: IEEE 754 defines its division by zero." That holds at run time. In a constant evaluation, C++ makes a division by zero undefined for every type, so `constexpr Line<double> r = x / 0.0;` fails on both compilers with their own error (probe 6: GCC "'(1.0e+0 / 0.0)' is not a constant expression"). The comment should say so.
- `std::numeric_limits<T>::min()` divided by −1 overflows. That is undefined at run time, and a constant evaluation fails (probe 7). This is the scalar's own arithmetic, like any signed overflow in a sum, but the comment of the one operation that names an integer precondition could mention it.
- The check runs when `detail::integer_limits<T> && std::equality_comparable<T>`. The comment names only `is_integer`. An integer-like type whose limits say `is_integer` but which has no `==`, or which leaves out `digits`, `min`, or `max`, is silently not checked (C8, hidden rule). Either state the full rule or drop the `equality_comparable` guard and let such a type fail to compile.

### F2. `requires(!detail::same_layout_v<A, B>)` keeps same-type sums inside the compile limits, and no test pins it. `sum_layout<Alg, A, A>` is not the layout of `x + x`. Minor; does not block; before release.

`linear.hpp:93-115`, `:253-258`, `:282-287`; decision 0167 ("so that the reader sees the two cases are disjoint rather than relying on partial ordering").

- Without the constraint, partial ordering still picks the same-type overload, so every value test passes. But substituting the two-layout overload's return type then evaluates `merge` of the layout with itself. A same-type sum of `full<8>` on Clang 23 and of `full<10>` on GCC 16 then fails to compile (my mutant and `limits.cpp`). The header's "A sum of one type, a scaling, and a negation cost no constant evaluation beyond the multivector's own" depends on the constraint, and on both compilers checking constraints before they substitute into the return type. Decision 0167 gives a different reason, so a maintainer could delete the clause as redundant.
- `sum_layout<Alg, A, B>` is the result layout of `x + y` only when A and B differ. For A = B it is the canonical reordering of A, while `x + x` keeps A. The comment says so. Even so, generic code that declares `mv<Alg, sum_layout<Alg, A, B>, T> f(X x, Y y) { return x + y; }` fails to compile exactly when the two types agree. Every other public `*_layout` name is the result layout of its operation for every argument. Hyrum's law applies once it ships.
- Suggested fix, which closes both: specialize `sum_layout<Alg, A, A>` to A. Then `sum_layout` is always the layout of `x + y`, and a same-type sum evaluates no merge even if the constraint goes. Add a test that a same-type sum of `full<8>` builds. It takes about 0.6 s on Clang (`-fsyntax-only`) and fails there without the constraint, while `full<7>` plus itself builds either way, so it would not catch the mutant. With the specialization, the type assertion `sum_layout<Alg, line_layout, line_layout> == line_layout` serves as well. Without the specialization, a test that keeps the constraint load-bearing, plus a comment on why it is there.

### F3. Two constraints no test pins. Low; does not block (tests only).

- `operator/`'s `requires detail::scalar_has_division<T>` (`linear.hpp:360`). Remove it and every test passes. A requires-expression would then answer yes for `x / s` over a scalar without `/`, such as the test file's own `mat2`, and the call would fail inside the body instead. One line kills it: `static_assert(!can_divide<Line<mat2>, mat2>);`.
- `multivector<X>` in `scalar_of_another_type` (`linear.hpp:304`). Every probed type (`widget`, `gadget`, `std::complex`, `std::string`) lacks a member named `scalar_type`, so `typename X::scalar_type` already rejects them. A user type such as `struct grid { using scalar_type = double; };`, a common member name in numeric code, would kill the mutant. With the clause lost, `2 * grid{}` would reach the catch-all and report the multivector message for a type that is not a multivector. Add such a type to `scaling_user_code`.

### F4. `part`'s rejecting overload has a deduced return type, so a requires-expression that probes it is a hard error, and nothing says so. Low; does not block; before release.

`include/galoot/core/mv.hpp:1072-1088` (the catch-all at `:1077-1088`), criterion 5, the checklist item on probes.

`template <class Target, ...> requires(!multivector_of<...>) constexpr auto part(...)`: deducing `auto` instantiates the body, so `requires(const Line& x) { core::part<double>(x); }` stops compilation with the part message on both compilers (`probes/part_probe.cpp`). It answers neither yes nor no. The sums, scalings, and `get` answer yes, and their comments say so. `part`'s comment talks only about avoiding a second error. The form is copied from `truncate` (`mv.hpp:1025-1036`), which behaves the same. Either declare the return type, `std::remove_cvref_t<Target>` when it is default-initializable and otherwise the input's type, which `truncate` already computes in its body, or state in both comments that a probe is a hard error. Add the probe test that criterion 5 asks for.

### F5. The scalar-type message gives only the double example, and the exact-type rule meets every integer type except `int`. Low; does not block; before release (the texts are pinned).

`linear.hpp:393-421`; `test/CMakeLists.txt` (`linear_scalar_type`).

`2 * x` is rejected for a `std::int64_t` multivector, the scalar type that `linear_test.cpp` itself uses throughout (`std::int64_t{1} * a`, `std::int64_t{-1} * b`). The message then says "write it in that type, as 2.0 for 2 when the scalar type is double". The fix it names does not apply, and Clang prints `std::is_same_v<int, long>` (probe 2), not `std::int64_t`. The same holds for `x * 2.0` over float (the fix is `2.0f`), `2.0 * x` over `std::complex<double>`, and `2 * x` over the rational. The rule is the plan's choice, and widening it later is additive (decision 0167). The message can still name the general fix: "...; convert it to the multivector's scalar type first, as 2.0 for 2 over double or std::int64_t{2} over std::int64_t". Changing a pinned text is a listed test change (W9), so it is cheaper now than after release.

### F6. CONVENTIONS 4.5, version 1.8, reads "what they drop is meant to be nonzero". Low; for the owner (C10); does not block.

`docs/agent/governance/CONVENTIONS.md:62`. ## 7. Usability checklist

Task first. From the examples of `linear.hpp` and `mv.hpp` alone, the three tasks are:

1. Build a motor-shaped value from a line and the antiscalar, and read a coefficient: `auto m = a + Antiscalar{1}; get<"e34">(m)`. The example gives the result's blades and the sign on e34, and `Motor{m}` converts it (the header comment's "Type{m}"). Worked first time.
2. Scale, divide, and negate a line: `2.0 * a`, `a / 4.0`, `-a`, all a `Line`. Worked. `2 * a` gives one clear error. Over `std::int64_t`, though, the message's fix does not fit (F5).
3. Take the line part of a motor whose scalar is nonzero: `part<Line>(turn)`. Worked, with no check in a checking build.

I read the implementation to learn three things: that same-type sums escape the merge limit only through the constraint (F2); that a requires-expression on `part` is a hard error (F4); and which types the zero check covers (F1).

Names:
- [x] Field terms or full words: `part` (the field's "grade part"), `has_name`, `sum_layout`.
- [x] One meaning, nothing the standard library means differently: `part` is in no standard header. `has_name` now says what it tests: an oriented name that `get` reads. Its comment draws the distinction from "holds the blade". No stragglers in code or user documentation.
- [~] Similar things look alike: `part` mirrors `truncate` in both forms and in its message. `sum_layout` breaks the `*_layout` pattern at A = B (F2).

Construction and conversion:
- [x] No new constructors. Results are values of the input's type or of a canonical set, converted explicitly (`Motor{m}`).
- [x] Default construction unchanged (zero).
- [x] No implicit lossy conversion: a scalar of another type is rejected, never converted, so `2.5 * x` over integers cannot truncate. `part` names its loss.
- [x] No hidden default: the scalar type is the operands'. The checking mode does not change `part`. Integer division's truncation is stated.

Misuse and diagnostics:
- [x] Each misuse in the catalogue (mixed algebras and scalars for `+` and `-`, a scalar of another type for the three spellings, the zero divisor, `part`'s five bad targets, the five ring faults and their order) has a compile-fail or expect-output test on both compilers that requires the literal message.
- [x] One error each, with the message on the first error line, also as `auto r = ...` (my probes 1 to 4, 14, 15, 17, 18; the tests). The zero divisor in a constant evaluation shows its message on the echoed source line.
- [~] The message starts with the operation as written and gives the fix after a semicolon, with no internal names. The scalar-type fix fits only double (F5).
- [x] Context lines: Clang prints `std::is_same_v<int, double>`, the two types in the order written. GCC adds "'int' is not the same as 'double'". Layouts still print as masks on GCC, a known limit.
- [x] Distinct causes give distinct messages, including the five ring requirements. When both algebra and scalar differ, the algebra message wins, as for the products.
- [~] Probes: the documentation says a requires-expression answers yes for the sums and scalings. For `part`, a probe is a hard error, and nothing says so (F4).

Semantics and cost:
- [x] What is discarded is named: `part` and `truncate`, each with its check stated. Sums say which blades the result holds. Negation and one-sided blades state their signed zeros.
- [x] `auto r = f(a, b);` is safe: every result is a value, and the rejecting overloads return values (no proxy, no reference).
- [x] Exact comparisons are `==`.
- [~] Cost: the header and `sum_layout` state the merge cost and the measured limits with the workaround. The guarantee for same-type sums rests on an untested constraint (F2).

Examples and readability:
- [x] The examples compile with a prelude and give the stated values (`probes/examples.cpp`). They mix no `^` or `&`.
- [x] A maintainer finds each behavior from its name: the vector-space operations in `linear.hpp`, `part` beside `truncate`, and the five ring clauses in one place.

Before release, the interface choices this unit fixes that cost more to change later (Hyrum's law):

1. `sum_layout<Alg, A, B>`, its argument order, and its value at A = B (F2).
2. The exact-scalar-type rule for `s * a`, `a * s`, `a / s` (widening later is additive) and the pinned texts of its three messages (F5).
3. `part<Blades>(x)` and `part<Type>(x)`, and their probe behavior (F4).
4. `has_name` with no alias for `has_blade`. Nothing has shipped, so nothing breaks now.
5. The order of the five ring-operation checks, which decision 0169 declares part of the interface.
6. The signed-zero behavior of one-sided blades and of negation.
7. Requires-expressions answering yes for mismatched sums and for scalars of another type.
8. No compound assignment and no unary `+` (F7a).
