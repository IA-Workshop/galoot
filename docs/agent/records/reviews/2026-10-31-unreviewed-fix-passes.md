## Findings

**Blocking (needs a fix commit)**
- A1. `merge` misses a mask repeated in the second input when the first input holds that mask (`blade_set.hpp:272-279`): `from_second[at]` records only the input that inserted the entry first, so a second hit from B compares against A's entry and takes the "other input" branch. `merge<{e1:+1}, {e1:+1, e1:+1}>` is accepted silently, and `merge<{e1:+1}, {e1:+1, e1:-1}>` reports only "opposite signs". The documented contract ("no mask appears twice in one set … each is checked at compile time") and decision 0092 ("merge checks every sign and every mask of both inputs") are therefore false, though the output is still a valid set. Keep two flags per entry (`in_first`, `in_second`); a repeat is the flag of the current input already being set. Add `merge<{e1}, {e1, e1}>` requiring "holds one mask twice" and a note to 0092.

**Non-blocking**
- A2. The removed guard hid a false message, not only a true one: `merge<{e1:0}, {e1:+1}>` now prints both "a set holds a sign other than +1 or -1" and the false "the two sets hold one blade with opposite signs". At 7595151, which still had the guard, only the first appeared, so the commit message and 0092's claim that the guard hid only a true second message are wrong. Set `opposite_signs` only when both signs are ±1 and differ, and add a test with FORBID "opposite signs".
- A3. Test gaps shown by surviving mutants: no test has a bad sign in the second input; `merge_no_flag_shift` (deleting `u.from_second[j] = u.from_second[j - 1]`) survives the suite yet wrongly rejects valid merges (`merge<blades<3,"e2">, blades<3,"e3 e1 e2">>` fails with "holds one mask twice"; 17 of the reviewer's random merges fail), so add a valid merge whose second input is out of canonical order and shares a mask with the first; `merge_repeat_first_only` is A1's test.
- A4. `index_of` now costs about three times as much to constant-evaluate: looking up every blade of `full<10>` rises from 21.3 G to 62.6 G instructions on GCC and from 38.4 G to 110.1 G on Clang (n = 9: 6.1 to 16.7 G and 8.6 to 25.7 G), because `look_up` scans the whole set and checks each sign on top of the position search. This matters for the multivector unit, where every coefficient access is a lookup. The sign check cannot change the returned position. A measured alternative (the position search, then a scan from the next position for a repeat, no sign check) costs 38.2 G on GCC and 63.0 G on Clang, about 1.7 times the old cost. Adopt it or record the measured cost in 0092. The new checks cost `merge` only +0.3% (Clang steps) and +0.7% (GCC operations).
- A5. `index_count_exactly_one` survives (`index_of_absent` could FORBID "twice"); lines 59-61 say "merge and index_of check it" though `index_of` checks only the looked-up mask; `is_sign` lacks `[[nodiscard]]` and `noexcept` (consistent with the other detail helpers).
- A6. The limit for `merge` is much lower than the documented limits (pre-existing): insertion is O(K²); at default limits Clang fails `merge<full<8>, full<8>>` (about 2.38 M steps against the 1,048,576 default; `full<7>` passes) and GCC fails `full<10>` (passes `full<9>`). State the `merge` bound in the header and the 0090 note.
