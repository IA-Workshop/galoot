- **After the script:** `main`, a fast-forward from `c95fee51` to `1655ef33` (`git rev-list --count origin/main..main` = 234, `main..origin/main` = 0; about 4.2 MB as a thin pack, by `git pack-objects --stdout | wc -c`); `master`, a fast-forward from `2383e6df` to the new merge, whose first parent is `2383e6df` (one commit; its tree is `main`'s, so no new blobs); `1.0.0`, nothing; `1.0.1`, one new tag object.
- **Pushing 1.0.0 again is harmless.** The remote's `refs/tags/1.0.0` is the same object `95a088ec`, so git reports it up to date and sends nothing. Had it differed, the push of that tag would be rejected, since git never updates an existing tag without force.
- The push is not atomic: if the remote refused one ref (a protection rule, say), the others could still land. `git push --atomic origin main master 1.0.0 1.0.1` makes it all or nothing; GitHub supports it (note, N3).
