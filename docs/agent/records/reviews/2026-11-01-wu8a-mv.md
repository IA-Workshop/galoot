## 3. Findings, most severe first

### F1 (medium, blocks): four compile-fail tests find their required literal in their own file name

`expect_output.cmake` searches the whole compiler output, and every diagnostic line starts with the source path. The affected tests:

- `core.mv_narrowing_int` and `core.mv_narrowing_float` require "narrow", and their files are `mv_narrowing_*_fail.cpp`.
- `core.mv_not_metric_like` and `core.blade_set_blades_not_metric_like` require "metric_like", and their files are `*not_metric_like_fail.cpp`.

So each passes on any compile error at all. With `ONE_ERROR` on the narrowing tests, every error line "holds the message", so that check does nothing there either.

Evidence:

- A file with these four names that contains only `int x = undeclared_name;` passes `expect_output.cmake` with each test's own arguments, on both compilers.
- The mutant `mv_alg_unconstrained` (mv's `metric_like Alg` replaced by `class Alg`) survives on gcc-debug and clang-debug.
- The mutant `blades_unconstrained` is not caught by `core.blade_set_blades_not_metric_like`. Only `core.blade_set_names_zero`, whose file name lacks the literal, kills it.

So criterion 3 (narrowing) and criterion 11a (rejection of a tag that is not `metric_like`) are weaker than the Outcome reports. The same flaw exists before this unit in `core.metric_like_no_generators`, `core.plan_not_metric_like`, and `core.plan_map_not_metric_like`; I report those under W9 and leave them.

Resolution, both needed:
- In `galoot_add_compile_fail_test`, stop at configure time when a MESSAGE or REQUIRE literal occurs in the source's path.
- Either rename the files, or require literals that no path holds: the compilers' "narrowing conversion of" and "cannot be narrowed", and "does not satisfy 'metric_like'" / "metric_like<int>".

### F2 (low): narrowing a double into a float layout is two errors under the project's flags

On both compilers the call gives the narrowing error and also the `-Wfloat-conversion` / `-Wimplicit-float-conversion` error, on the same line. That breaks the checklist's "one misuse, one error" for a user with the project's warnings. The `ONE_ERROR` on `core.mv_narrowing_float` hides it (F1).

Resolution: drop `ONE_ERROR` from that test and record the two-error text as compiler behavior, or document the case.

### F3 (medium, blocks): three stated contracts have no test that can fail

Each of these mutants survives on both presets:

- `equality_requires_removed`: the comment says `==` "Declared only for a scalar with ==, so that a scalar without one ... still gives a multivector type, and generic code that asks is told it has no ==". No test uses such a scalar. My probe confirms the behaviour is right today: a lane scalar with no `==` is a `ring_scalar`, gives a type, and is not `equality_comparable`.
- `ring_requires_equality`: "Equality is not required" in `ring_scalar` is never tested from the accepting side.
- `catchall_k1_not_explicit`: making the count catch-all non-explicit for one value makes `std::is_convertible_v<double, Line<double>>` true. Nothing tests it.
- Related, `catchall_counts_ignored_for_one`: no test passes one plain value to a multi-blade type (`Line l{2.0};`, a likely mistake). So the count message for that case is unpinned.

Resolution:
- add a lane-like scalar to `mv_test.cpp`: `ring_scalar` true, `mv` over it instantiates, `!std::equality_comparable`;
- add `static_assert(!std::is_convertible_v<double, Line<double>>)`;
- add a compile-fail test for `Line l{2.0}` that requires the count literal and "1 == 6".

### F4 (low): a scalar that is not semiregular gets the compiler's constraint text

Probes: a fixed-point type without a default constructor, and a move-only type. Both are plausible user scalars.

- GCC: one top-level "template constraint failure" that prints the full requires-clause, with a nested error; 42 to 43 lines.
- Clang: two `error:` lines, the second from inside `<concepts>`; 28 to 29 lines.

No literal message and no compile-fail test. The `///` comment does say "or the type does not match".

Resolution: constrain `T` by a weaker named concept (for example `std::destructible`) and assert `std::semiregular` in the body with a literal, as decision 0152 does for `ring_scalar`; or add a test labeled as a record of compiler behavior.

### F5 (low, before release): a copy from a class derived from `mv` hits the count message

With `struct MyLine : Line { using Line::Line; };`, `Line l(m);` fails with "mv: give one value for each component ... '1 == 6'" on both compilers, because `multivector<MyLine&>` is false and the catch-all's exact match beats the derived-to-base copy. `Line l = m;` compiles, because that catch-all is explicit.

Resolution: exclude types derived from a multivector in the catch-all's constraint, or state the case in the comment.

### F6 (low): a header comment overstates what Clang prints

The comment says: "Naming the layout and the type, as above, also lets Clang print those names in its diagnostics."

In the count error and in all seven `get` errors, Clang's context names `mv<rga3, blade_set<6>{{{{9, -1}, ...}}}, double>`, and the record's L and I texts are identical for cases 1, 5, and 6. Only the candidate notes of the implicit conversion (case 8) show `'Motor' (aka ...)`. So the checklist item "context lines show the user's terms" is not met. This is already the owner's open question.

Resolution: "lets Clang name them in some diagnostics, such as the candidates of a failed conversion".

### F7 (low): the defect comment, the lesson, and the regression test describe the GCC trigger more broadly than observed

I reproduced the reproducer exactly: V1 and V4 are wrong on GCC at -O0 and -O2; Clang is right throughout. My own variants, with `struct q { long n = 0; long d = 1; }`, show the trigger is narrower:

- a write at place 0 or 1 does not damage the array; places 2 and up damage from the written place on;
- a local `std::array<q, 6> a{}` is not affected, nor is a second class with the same element type;
- the `= {}` form and a template storage like the pre-fix `mv` are affected;
- `box b;` (default-initialization) is affected as well as `box b{}`;
- the per-place initializer is right.

`mv.hpp` states the mechanism ("reuses one shared initializer") as fact, and lesson 0065 speaks of "a run-time value-initialization of an array of a class type". The regression test writes at place 2, so it would stop catching the defect if someone moved the write to place 0 or 1.

Resolution:
- word the comment as observed behaviour;
- narrow the lesson's description to an array that is a default member initializer;
- say in the test why the write is at place 2.

Completeness of the workaround: no second instance today. Every library array element type (`oriented_blade`, `term`, `plan_term`, `typed_term`, `bool`, `char`, `std::size_t`) has an all-zero-bits zero, and the rational sits in a member array only inside `mv`. Test-local arrays such as `counting<T, K>()` are not affected (my W=3 variant).

### F8 (low): a positional `get<0>(line)` gives a deduction failure in internal terms

This is a likely mistake for anyone used to `std::get`, and the checklist names `get` as a standard-library clash.

- GCC: one top-level error, 68 lines, printing `detail::name_list`, `coefficient_reference`, and both requires-clauses.
- Clang: one error with two notes about `detail::name_list` deduction.

The name is ruled (decision 0153).

Resolution, optional: a separate `template <std::size_t I, multivector X>` catch-all with a literal such as "get: takes a blade name, as in get<\"e41\">(x); read a coefficient by position with coefficients[i]".

### F9 (low): the rational's cross-cancellation in `*` is untested

The mutant `rational_product_no_cancel` survives on both presets. A missing cancellation would abort, not give a wrong value.

Resolution: `rational{2^62, 3} * rational{3, 2^62} == rational{1}`.

## 6. Usability checklist

Tasks, written after reading the header (section 1):
1. declare a rigid(3) Line, make the z axis, read e43 and write e23;
2. make a zero motor and compare two lines exactly;
3. ask in generic code whether a type holds e41.

Tasks 1 and 2 follow from the examples. Task 3 needed the `get` comment to learn that a `requires`-probe answers yes and that `has_blade` is the question to ask.

Not ticked:
- `get` is a standard-library name (F8);
- the blade-set builders do not look alike: `blades<Alg>` beside `full<N>` and `of_grade<N, K>` (ruled, decision 0157);
- the likely-misuse tests: F1, plus F4 and the single value of F3 untested;
- one error per misuse: F2, and F4 on Clang;
- the fix after a semicolon (F10);
- the context lines in the user's terms (F6).

Ticked: zero by default; exact `==`; no hidden defaults; explicit single-value construction; data-only concepts with the wrong-answer probes documented; `auto r = get<...>(temp)` is a copy; costs and limits stated; the examples compile.

Before release, interface points that will cost more to change later:
- `auto [c] = line;` compiles today and binds the whole array;
- copies from derived types (F5);
- `std::is_constructible_v<Line, double, double, double>` is true;
- the public names `coefficients`, `layout`, `component_count`, `algebra_type`;
- `get` found only by argument-dependent lookup.
