**F8 and the bound (brief item b).** I checked `detail::holds_exactly<T>` against an independent reference (`exact.cpp`) on 408,449 coefficients: every ±2^k and ±(2^k ± 1), every odd part of every width shifted by every k, INT64_MIN and INT64_MAX, and 400,000 random values with random trailing zeros (seed 20261101). The references are:

- for a signed integer type, the round trip `int64 -> T -> int64`;
- for an unsigned type, the stated rule |c| ≤ max();
- for a binary floating type, the round trip through `long double`, which holds every `int64` exactly;
- for a type with only half-precision limits, the bound (2^p − 1) 2^(emax − p) together with divisibility, a formulation independent of the header's.

The types were `signed char`, `char`, `short`, `int`, `long`, `long long`, `int32`, `int64`, `wchar_t`, the four unsigned widths, `char16_t`, `char32_t`, `float`, `double`, `long double`, and the half type, plus `std::float16_t`, `std::bfloat16_t`, `std::float32_t`, `std::float64_t`, and `std::float128_t` on GCC. There were **0 mismatches on both compilers** (`out/exact-gcc.txt`, `out/exact-clang.txt`).

So, for any type whose `numeric_limits` is complete, the check neither admits an inexact coefficient nor rejects an exact one. The signed range is checked on both sides (−32768 and 32767 are held by `short`, −32769 and 32768 are not, and these four are asserted in the tests). A float's odd part must fit `digits`, and |c| < 2^max_exponent (2^15 is held by the half type, 2^16 is not; `std::float16_t`'s real conversion agrees). For `long double` and wider, every `int64` is held. The unsigned rule is unchanged from `6c9df63` and is only now stated in the comment.

The tests pin every bound tightly enough that changing it by one is caught: my mutants `odd_part_not_divided`, `exponent_strict`, `odd_bits_one_more`, `signed_guard_too_low`, and `signed_as_magnitude` were each killed by a static_assert in `mv_test.cpp`.

## 5. Findings, most severe first

### D1. The non-explicit braced-list catch-all breaks valid code, changes `std::is_convertible_v`, and departs from STYLE S8. Major; blocks (small fix).

`include/galoot/core/mv.hpp:589-605`, `constexpr mv(const std::remove_cvref_t<T> (& /*values*/)[N])` without `explicit` (hci C1, decision 0150, review-fix item 4).

The parameter binds to a braced list, and also to any lvalue C array of T. Without `explicit`, every `T[N]` now converts implicitly to every mv over T (`out/traits-*.txt`):

- `std::is_convertible_v<double(&)[4], Point<double>>` goes from false to true. The same holds for `double[6]` into a four-blade Point, and for `double(&)[1]` into `Scalar`.

The consequences, from `c1.cpp`, before and after, on both compilers (`out/c1-case*`):

1. `g(raw)`, with overloads `g(const Point&)` and `g(std::span<const double>)` and `double raw[4]`: before, it compiles and calls the span overload. After, it is "call of overloaded 'g(double [4])' is ambiguous" on GCC and "call to 'g' is ambiguous" on Clang. **A valid program stops compiling.**
2. `std::variant<Point, std::span<const double>> v = raw;`: before, it compiles and holds the span. After, it does not compile (GCC: conversion error; Clang: the catch-all's static_assert, 3 errors).
3. Generic code that dispatches on `std::is_convertible_v<const X&, Point>`: given a C array, it now takes the convertible branch. Had that branch converted, the catch-all would fire.

The comment says "it converts nothing: only a braced list or an array of T reaches it". That is true of the body, not of the traits or of overload resolution. The decision gives as its reason for keeping the other catch-alls explicit that a non-explicit one "changes std::is_convertible_v answers that generic code relies on", and this one does exactly that, undocumented (the checklist: "the documentation says which probes give a wrong answer"). The hci reading's evidence for C1 ("no other case, trait, or the control program changed") covered braced lists only, not array lvalues.

The process point: STYLE S8 says "single-argument constructors are `explicit`". Reading it as not applying to a constructor that only rejects is an interpretation of ratified text. The constitution makes a departure from a provision the owner's decision, not an agent's. The lint suppressions (`cppcoreguidelines-explicit-constructor`, `misc-explicit-constructor`; both exist in clang-tidy 23 and are enabled by `cppcoreguidelines-*` and `misc-*`) are mechanically correct and needed. The reason given beside them points to the comment, whose claim is the one shown wrong above.

Fix, either of:

- (a) Restore `explicit`, and make `core.mv_coefficients_as_braced_list_copy` a compiler-wording test or remove it. This is the state of `6c9df63`.
- (b) Take the braced list by rvalue reference, `std::remove_cvref_t<T> (&& /*values*/)[N]`, which a braced list binds to and an lvalue array does not. In a scratch copy of the header (one line changed; `alt/` beside this file), `Point p = {{1, 2, 3, 1}};`, `Point p{{1, 2, 3, 1}};`, and `Point{std::array}` each still gave one error with the literal on both compilers. Cases 1 to 3 above returned to their `6c9df63` behavior (span chosen, variant compiles, `is_convertible` false), and `const Point p = raw;` is the compiler's error again. **Not run through the suite**, and an xvalue array (`std::move(raw)`) still converts implicitly. This option keeps a non-explicit single-argument constructor, so it still needs the owner's ruling on S8.

Before release: whichever is chosen, it fixes `std::is_convertible_v<T(&)[N], mv>` for users (Hyrum's law).

### D2. A one-blade value from a value T accepts only explicitly is now 114 lines on GCC. Low; does not block.

`mv.hpp:388-390` (F2). `Scalar<rational>{1}`, `Scalar<double>{explicit_to_double{}}`, and `Scalar<std::complex<float>>{std::complex<double>{}}` now reach no constructor. GCC prints "no matching function for call to ..." with 11 candidates in masks, 114 lines (`out/f2-case2-gcc-after.txt`); Clang prints 44 lines.

At `6c9df63` each gave a one-line literal, but the wrong one (the array message). This is the outcome the first review proposed, and decision 0150's review-fix item 1 records it, so it is no regression of intent. It is still the longest diagnostic among the single-value cases.

Possible later fix: a catch-all for a single argument that T is constructible from but that does not convert to T, in a one-blade layout, with a message such as "mv: the scalar type is made from this value only explicitly; write T(value)". This would make `std::is_constructible_v` true again for those three rows, so it is a trade to decide before release.

### D3. A partial `numeric_limits` specialization is no longer checked. Low, confirmed by probe; does not block.

`mv.hpp:614-630`. The concepts now also require `is_signed`, `digits`, and `min()` (integer) or `max_exponent` (float). A specialization that defines `is_integer` and `max()` but not `min()`, or `digits` but not `max_exponent`, now falls through to "not checked".

`partial.cpp`: a specialization with `is_integer` and `max() = 127` rejects 200 at `6c9df63` and accepts it at `00235b8`. A float specialization with 11 digits and no `max_exponent` rejects 4097 before and accepts it after (`out/partial-*.txt`). A product over such a type would then round, or overflow, silently.

A specialization that meets the requirements of the primary template ([namespace.std]) has every member, so no conforming type is affected, and decision 0154's review-fix item 1 states the choice. Still, the check now admits coefficients that it rejected before, for the very kind of program-defined type it was meant to serve. Safer: when `max_exponent` is missing, keep the bound on `digits`; when `min()` or `is_signed` is missing, keep |c| ≤ max(); or reject the type with a message.

### D4. `apply`'s Requires paragraph states the bound only in part. Nit.

`mv.hpp:760-764` says "a signed integer type within min() to max(), a binary floating type when the odd part of |c| fits its digits". It leaves out the exponent bound and the unsigned rule, which `holds_exactly`'s comment (`:632-640`) states. One clause fixes it.
