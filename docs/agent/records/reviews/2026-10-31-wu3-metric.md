## Findings

**Blocking**
- B1. `metric.hpp` `is_null(i)` documents "Requires: i < N" but does not check it. `rigid<3>().is_null(7)` reads out of bounds with no diagnostic in a user's build; the tidy suppression's reason leans on test builds checking each access. Add `GALOOT_ASSERT(i < N, ...)` and a run-time abort test, more so once the bounds-check reminders are excluded in `.clang-tidy`.

**Non-blocking**
- N1. `metric_like` hard-errors instead of returning false when a tag's `value` is not usable in a constant expression (a static non-constexpr `value`; a non-static member named `value` on GCC). Add a `requires { typename std::bool_constant<...>; }` guard, checked on both compilers.
- N2. The largest number of generators does not travel with the algebra: later templates written `template <metric_like Alg>` reject any tag with n > 16, even one built with `R<20, 32>`, so raising the bound means editing `max_generators` or changing every later interface, against decision 0004. Carry the bound with the tag, or have the concept enforce only the mask width and keep 16 as the factories' default. Needs an owner decision before the blade-set unit.
- N3. The comment claims `int` has at least 32 bits; C++ guarantees 16. Goes away when the bound is derived from `numeric_limits`.
- N4. `p + q + r` overflows for huge counts and gives raw compiler text; the `size_t` form wraps (`R<SIZE_MAX, 0, 2>` gives N = 1). Check each count against the bound before summing.
- N5. `R<P, Q, R>()` as written does not compile: a template parameter named `R` on a function template named `R` is ill-formed on both compilers. Rename the third parameter. A negative count then fails by narrowing with readable text but not the literal message.
- N6. The tests were committed with the code they judge (W9); record it, and commit tests separately in the follow-up.
- N7. No test rejects a lookalike type in `metric_like` (a struct with the three members that is not a `metric`); this lets the dropped-`is_metric_v` mutant survive.
- N8. The plan outcome lacks a verification and validation status line; the mutation-script lesson sits in the plan, not in the lessons directory; decision numbering jumps to 0060.
- N9. `from_gram<MaxN, N>` puts MaxN first while `R<N, MaxN>` puts N first; `from_gram<3>(...)` sets MaxN.
- N10. Nits: `gram` has no `///` comment; a plain `//` comment sits between `from_gram`'s `///` block and its declaration.
- N11. The `metric_like` cost was measured at one size (n = 16); three sizes are needed for the growth rule.
- N12. Merge mechanics: `develop` must be merged in; after core-bits, two one-line conflicts.
- N13. A ragged or non-square matrix to `from_gram` is rejected with raw "no matching function" text; the catch-all form could reach it, or the comment states "must be square".

Recommendations on the owner questions: derive N (rename the third parameter, check counts first, drop the sum and negative-count tests, keep the n = 0 and n > bound messages); derive the entry bound from `numeric_limits` (32767 for `int` confirmed), constrain any entry parameter with a named concept, and note that the bound only buys an early readable message because larger minors can still overflow as a compile error, never silently; an entry-type parameter with one present user goes against the rule on unused generality, which is the owner's call; exclude the two tidy checks in `.clang-tidy` with the reason, paired with B1.
