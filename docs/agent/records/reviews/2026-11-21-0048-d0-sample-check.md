## Findings, most severe first

### 1. `plan.hpp:302-307`: a precondition that is undefined behavior in an unchecked build is classed delete (confirmed, important)

Row 247 of the table covers the `Requires:` and `Guarantees:` lines of `collect_result` (`include/galoot/core/plan.hpp:302-307` at `01dce7f`) and classes them `delete`, waiting for the detail ruling, with the note "restates the summary, adding only that later places are not written". The summary it cites (`:299-301`) does not say that `out` must have a place for every distinct blade. The text it deletes does: "`out` has a place for every distinct blade, checked by GALOOT_ASSERT; plan.size() places always suffice."

The code writes `out[at]` and shifts `out[j] = out[j - 1]` after `GALOOT_ASSERT(size < out.size(), ...)` (`plan.hpp:319`). With checking off at run time the assertion is not evaluated, and a span too small gives an out-of-bounds write: undefined behavior. A constant evaluation always checks, so a user never meets it today. But the author's own rule keeps this class in full, on `detail` helpers too: `term_list::add` (`blade_product.hpp:132-140`), `low_bits` and `in_algebra` (`bits.hpp:45-47`, `:58-60`) and `unary_term` are kept for the same reason. This row is the one site of that kind I found that the table treats the other way. The README's list of "preconditions kept in full" does not name it either.

Fix: class the `Requires:` lines (`302-303`) as keep, with the same note the others carry, and leave `304-307` as the table has them. The README's count of eleven preconditions becomes twelve. Because the row waits for the detail ruling, no unit could have acted on it yet; the hand-over is wrong, nothing is lost.

### 2. `transform.hpp:492-495`: a delete that the named target does not fully repeat (confirmed, important)

Row 675 classes the "price" sentence of `padded_magnitude` as `delete`, waiting for nothing, with target `limits.md`, "The rounding check". The sentence says the padding puts "a floor under every tolerance, about K λ W for W the number of padded products on the path". The limits page holds the two numbers (near 10^-306 in `double`, 10^-36 in `float`) and the 2^-41 case, but not the size of the floor in K, λ and W. `grep` finds "K λ W" only in `transform.hpp:492` and in decision 0180 (the 2026-11 addendum, item 3). So the fact survives in a decision record and nowhere that a maintainer of the header or a reader of the guide would look.

By the letter of the brief this is not an error, since the fact is not lost to the repository. It is a wrong verdict for the row's own stated test, which the README gives as "a delete row is marked as a repeat only where that text states the same facts". The neighbouring kept block (`:483-491`) explains why the padding is λ/u; the price of that choice is its consequence and belongs beside it. Recommended class: keep, or summary with the formula kept.

### 3. `bits.hpp:132`: a public contract deleted with no waiting condition (confirmed, minor)

Row 57 classes `/// Guarantees: returns -1 or +1, with u ∧ (s e_C) = +e_12...n.` as `delete`, waiting for nothing. It is the only public-contract delete in the table that does not wait for the S11 amendment (the other 27 do). Decision 0253 item 14 says that until the amendment is applied "no unit removes a contract from a header". The equation is repeated at `:126-129`, but "returns -1 or +1" is not. Change the wait to the S11 amendment, or class the line as keep.

### 4. Two deletes cite a home that holds only half of the text (confirmed, minor)

Rows 219 (`plan.hpp:63-66`) and 276 (`plan.hpp:624-627`) cite `plan.hpp:536-539` as the place that already says why the locals are `static constexpr`. That range gives the Clang half. The other half (GCC's cache of constant calls serves a repeated call, so a second generation would not show there, and the once-only check therefore runs on Clang only) is in neither range, and `plan.hpp:63-66` and `:627` are the two places in the headers that say it. It survives in `test/CMakeLists.txt` (the comment above `core.plan_evaluated_once`) and decision 0112, so nothing is lost; the cited target is not accurate. Row 219 also waits for nothing, while row 276 waits for the detail ruling. Fix: keep one of the two sentences, or name the test comment as the second home.

### 5. Row boundaries inside a sentence (confirmed, minor)

A unit that acts on the rows that wait for nothing, and leaves the others, would leave fragments:
- `unary.hpp:18-24` is delete (waits for nothing) and ends with "A class derived from mv is", and `:25-27`, which finishes the sentence, is move (waits for D3).
- `transform.hpp:589` is delete (waits for nothing) and holds "the line of the check, which a failed constant evaluation shows. It has"; `:587-588` is kept and ends "The message is on", and `:590-610` ("four causes:") moves after D3.
- `blade_set.hpp:577` is delete (waits for the S11 amendment) and is the middle line of a sentence whose first line is in the summary row `:571-576` and whose end is a kept pointer, `:578-579`.

The table's method says so ("the line goes with the row that holds most of it"), and the notes mention it for 589. Nothing is lost. A comment unit needs a rule that a row whose neighbor waits longer is rewritten, not cut. I suggest the README say it.

### 6. Illustrations that exist only in a deleted prologue (confirmed, minor)

Two deleted prologue sentences carry a concrete case that the cited guide page does not: `transform.hpp:24-29` (a motor of rigid(2) or conformal(3) has blades of odd grade; the guide gives only the general rule that grade and antigrade parity differ where n is odd), and `dual.hpp:60-70` (the bulk of a rigid(3) line holds e12, e13, e23, with the moment on e31 negated on e13, and `Line{bulk(l)}` reads it back). Both follow from the rules the guide states, so I rate neither a loss of a fact. The reference entries for `transform` and `bulk` are the natural place for them, so I suggest the two rows say "reference" in their notes.

## The baselines I recomputed by my own method

Prologue 702; `///` on public declarations 1,338; `///` on `detail` 443; `//` elsewhere 725. All four equal `baseline/comments.txt`, the table's own position column, and plan 0048 section 3.1.
