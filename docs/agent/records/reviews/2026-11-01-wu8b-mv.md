## 5. Findings, most severe first

### F1. Every product over `long double` fails to compile on GCC under the test flags. Major; blocks (small fix).

`include/galoot/core/mv.hpp:587-589`, in `detail::holds_exactly`:

```cpp
return limits::digits >= 64 ||
       magnitude <=
           (std::uint64_t{1} << static_cast<unsigned>(limits::digits));
```

On x86-64, `long double` has 64 digits. The `||` stops the shift from being evaluated, but GCC still checks the shift with a constant count of 64. It warns "left shift count >= width of type [-Wshift-count-overflow]", which is on by default, from inside a core header, for any `apply` over `long double`.

Under `-Werror` (the project's test flags, STYLE S4), that warning is an error. My probe was `apply<gp>(Point<long double>{1, 2, 3, 1}, Point<long double>{4, 5, 6, 1})`: GCC 16.2.1 stopped at `mv.hpp:589` with the project's flags and warned with no flags at all. Clang 23 accepts it. The selections are `review-wu8b:probe-more:g++:1` and `review-wu8b:probe-long-double:gcc-plain` in the run log.

`ring_scalar<long double>` is asserted true (`mv_test.cpp:512`), so this is a scalar the library says it accepts. It also hits any binary floating type with 64 or more digits, such as `__float128`.

Fix: split the branch with `if constexpr (limits::digits >= 64)`. Then add a product over `long double` to the tests, which would also kill the F4 mutant.

### F2. A single argument of a scalar with an explicit integer constructor gets the wrong message. Minor; should fix before merge.

`mv.hpp:372-374` (`not_a_coefficient`) and `533-539`. A single constructor argument counts as "not a coefficient" when it does not convert *implicitly* to T. The test rational's constructor from `std::int64_t` is `explicit`, so over the rational:

- `Line{1}` (six blades) gives "mv: give the coefficients one by one, not as one array or braced list; ..." on both compilers, where `Line{rational{1}}` gives the count message "1 == 6".
- A one-blade layout, `S{1}`, gives the same array message.

My probe is `review-wu8b:probe-single:*`. The user gave neither an array nor a braced list, so the message names a cause they did not commit. That fails the checklist item "distinct causes give distinct messages". A `Line<double>{std::complex<double>{}}` is told the same thing.

Suggested fix: classify by `std::constructible_from<T, Value>`. Then `Line{1}` gets the count message, and `S{1}` gets the compiler's account of the explicit constructor. It also helps to word the message so it does not assume an array, or to add an `is_array`/range test. This changes what `std::is_constructible_v` answers, so it belongs before release.

### F3. The test of truncate's check cannot see a defect after the first dropped place. Minor; should fix (test only).

`mv.hpp:772-778` loops over every dropped place. Every exact-scalar test that expects the check to fire puts the nonzero value in the *first* dropped place: the motor's scalar at place 0, with e1234 at place 7 kept zero (`mv_test.cpp:1895-1915`, `core.mv_truncate_consteval_nonzero*`, and the truncate programs). The conformal case drops a single place.

My mutant that `break`s after the first check passed all 56 `core.mv` tests. A defect that checks only one place, or skips the last, would let a nonzero e1234 drop silently over `std::int64_t`.

Fix: add a case with the scalar zero and e1234 nonzero, at compile time and in the truncate programs.

### F4. No product over a scalar with 64 or more digits is tested. Minor; fix with F1.

The guard of F1 is untested: changing `>= 64` to `> 64`, which is undefined behavior in a constant evaluation, survived. A `long double` case in the five-scalar test, or in the coefficient-check test, covers both F1 and this.

### F5. The likeliest lossy mistake, `const Point s = motor;`, keeps the compiler's message (departure 1). Minor; does not block; for the owner.

I judge the departure correct as reasoned. An `explicit` constructor is not a candidate in copy-initialization. A non-explicit catch-all would go against STYLE S8 and make `std::is_convertible_v<Motor, Point>` answer yes. `= delete("…")` is C++26, outside the baseline (S2).

Still, against the checklist, this mistake is the first of plan 0016's three likeliest, and it gives:

- no literal message;
- on GCC, an 811-character first line of masks (`diagnostics/wu8/wu8b/out/gcc-after-case8.txt`);
- on Clang, 28 lines of candidates.

Passing a Motor to a `Line` parameter (`g(m)`) behaves the same way (probe case 4). Decision 0155's WU8b section, item 3, puts the measured alternative before the owner. This review adds only that the cost falls on the most common form of the mistake.

### F6. The lossy conversion's comment does not say that `std::is_constructible_v<Line, Motor>` is true. Minor; does not block.

`mv.hpp:498-502`. The count catch-all and the array catch-all each state the probe they answer wrongly. The lossy catch-all does not, although the test "Probes of conversion answer as the constructors' comments say" (`mv_test.cpp:2040`) asserts it. Generic code that asks whether a Line can be made from a Motor is told yes. The checklist asks that "the documentation says which probes give a wrong answer". One sentence fixes it.

### F7. Two messages break the plan's own message style. Low; does not block.

Reading 21 and the checklist ask that a message start with the operation and give the fix after a semicolon.

- The coefficient check (`mv.hpp:711-713`) starts "the scalar type cannot hold ...", with no operation. Decision 0154 item 4 gives the reason: `apply` serves every product, and public names come in WU9. WU9 should give each product's catch-all its own prefix.
- The lossy conversion (`mv.hpp:506-507`) starts "conversion drops blades of its input: it is lossy, so request it ...". The fix follows a colon, not a semicolon, and there is no `mv:` prefix, unlike the other constructor messages. The wording is decision 0155 item 2's, which is ruled, so this is for the owner.

### F8. The coefficient check is conservative above 2^digits, and its message is then untrue. Low, plausible; does not block.

`holds_exactly` rejects any coefficient above 2^digits, even one the floating type holds exactly. For example, −2^25 in `float` comes from diag(8192, 4096). The message then says "cannot hold one of this product's exact coefficients", which is false for that coefficient.

The same goes for a coefficient of −2^15 in `short`, and of −2^63 in `std::int64_t` (whose magnitude is above max()). The bound is documented, "up to 2^digits", and no present plan reaches these values. If it ever matters, check "is representable" (for a float: |c| ≤ 2^digits, or c divisible by the right power of two) instead.

### F9. truncate's validity depends on whether the scalar is exact. Design note for the owner, before release.

CONVENTIONS 4.5 (version 1.7) and decision 0155 rule this, so it is not a defect. Over `std::int64_t` or the rational, `truncate<Line>(motor)` with a nonzero scalar part fails a constant evaluation, or aborts in checking mode. Over `double`, the same expression silently drops the scalar. The library has no named projection for a user who means to drop nonzero parts.

The checklist also names `truncate` as a name the standard library environment means differently (POSIX `truncate`, `std::trunc`). The comment's "It drops components, not digits" helps, and the test covering argument-dependent lookup beside `<unistd.h>` passes.

### F10. Misuses outside the catalogue get the compiler's text. Low; does not block; for WU9 and WU15.

`truncate<5>(motor)`: GCC gives 5 errors in 51 lines, Clang 1 error in 13. `Motor<double>{Line<float>{}}` (a scalar mismatch): GCC gives 113 lines, Clang 43. Both are as the plan expects. The scalar mismatch will be a common mistake once the public products exist.

## 7. Usability checklist

Task first. From the examples alone, the three tasks are:

1. Make a motor from a line: `Motor{line}`.
2. Take back the line of a motor that is known to be a line: `truncate<Line>(m)`.
3. Multiply two points, through `detail::apply` until WU9.

For task 2, I had to read the `///` comment to learn that truncate checks rather than projects (F9). For task 3, the user-facing call does not exist yet. I read no implementation to answer any of the three.

Names:
- [x] Field terms or full English words.
- [ ] One meaning, and none the standard library gives differently: `truncate` (F9). `apply` is in `detail` and always qualified.
- [x] Similar things look alike. `truncate` and `apply` both take the target as a template argument.

Construction and conversion:
- [x] The shortest way to make a value is correct: `Motor{line}`, three spellings.
- [x] Default-constructed results are zero, including the places of a target that no term reaches.
- [x] Lossy conversions are named and never implicit; lossless ones are explicit.
- [ ] No hidden default changes a result. Partly unmet: truncate's behavior depends on whether the scalar is exact (F9), and its run-time check on `GALOOT_CHECKING`, which is 0 when unset (documented in `assert.hpp`).

Misuse and diagnostics:
- [ ] Each likely misuse has a compile-fail test that requires the literal. The implicit lossy conversion is compiler wording, labeled (F5).
- [x] One error, with the message on the first error line, for the catalogued cases. `ONE_ERROR` passed on both compilers.
- [ ] Message style: F7.
- [ ] Context lines show the user's terms. GCC prints layouts as masks (WU8a's known cost, decision 0157).
- [ ] Distinct causes give distinct messages: F2.
- [ ] Probes documented: F6.

Semantics and cost:
- [x] Operations that discard components say so (truncate's comment).
- [x] `auto r = f(a, b)` is safe: `apply` and `truncate` return values.
- [x] Exact comparisons are `==`.
- [~] Cost stated: `apply`'s comment gives its limits and its one statement per term. The conversion and truncate comments do not state cost (nit).

Examples and readability:
- [x] `bare_user.cpp` compiles and is the idiom.
- [x] Each behavior has one place in the header.

## 8. Before release (interface changes this review suggests)

1. F2: classify a single argument by constructibility, not implicit convertibility. This changes `std::is_constructible_v` answers.
2. F5: whether the implicit lossy conversion gets a literal (a non-explicit catch-all) changes `std::is_convertible_v`.
3. F9: whether a named projection joins `truncate`, and whether `truncate` stays the name.
4. F6: probe answers that generic code may come to rely on, such as `std::is_constructible_v<Line, Motor>` being true.
5. Decision 0150's WU8b item 3: `typename mv<A, B, X>` is valid for every destructible X. Narrowing it later would break generic code.
