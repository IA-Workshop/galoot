## What I checked, and how

**1. The macro (`assert.hpp:20-38`, `:74`).** Preprocessed a probe that stringizes `GALOOT_ALWAYS_INLINE` with g++ 16.2.1 and clang++ 23.1.4, `-std=c++23`, for each of these command-line values of `GALOOT_FORCE_INLINE`. Results are the same on both compilers:

| Value | Result |
| --- | --- |
| not defined | `[[gnu::always_inline]]` |
| `-D` with no value (the compiler defines it as 1), `=1`, `=01`, `=0x1`, `=(1)`, `=true` | `[[gnu::always_inline]]` |
| `=0`, `=false` | empty |
| `=2`, `=-1` | `#error "GALOOT_FORCE_INLINE must be 0 or 1"` |
| `=` (empty) | an error, but the preprocessor's own (`operator '!=' has no left operand`; Clang: `invalid token at start of a preprocessor expression`), not the literal |
| `=1.0` | the preprocessor's own error (floating constant) |
| `=ON`, `=OFF`, `=yes`, any other identifier | **empty, with no diagnostic**: an undefined identifier in `#if` is 0 (finding m1) |

For comparison, `-DGALOOT_CHECKING=ON` is not silent: `GALOOT_CHECKING` is also used in a C++ expression (`checking_now`), so the compile fails with "'ON' was not declared". `GALOOT_FORCE_INLINE` appears only in `#if`, so nothing catches it. With `-Wundef` GCC warns ("'ON' is not defined, evaluates to '0'"); the test flags do not include `-Wundef`. A token-pasting check (`#if !CAT(IS_01_, GALOOT_FORCE_INLINE)` with `IS_01_0` and `IS_01_1` defined as 1) gives the literal `#error` for empty, `ON`, `true`, `01` and `2` on both compilers, and a paste error for `-1` and `(1)`. I compiled this as a probe and did not put it in the tree.

The expansion test (`test/core/force_inline_test.cpp`) compares the stringized expansion with `"[[gnu::always_inline]]"` or `""`, and the expected mode comes from `GALOOT_EXPECTED_FORCE_INLINE`, given separately. A missing expected value does not compile. The test can fail, and the mutants show it does.

**2. ODR and mixed modes.** Two units that include the core with different values define the same inline functions and templates with different token sequences (one carries the attribute). That breaks the one-definition rule, and no diagnostic is required. The guide says so in substance at `core.md:1049-1051` ("Every translation unit of a program should use the same mode, since the two modes give the core's functions different definitions"); the README and the header comment say nothing about it (m4). To see what the compilers do in practice, I linked a forced unit and an unforced one, each calling `wedge` on two rga3 points, with g++ and clang++ at `-O0` and `-O2`. All four links worked and gave equal values. The unforced unit emits weak out-of-line copies at `-O0` and the linker keeps one. Within Galoot's own build no program mixes modes. `galoot_doctest_main` compiles only doctest, and `galoot_test_support` and `galoot_reference_kernels` are INTERFACE targets, so each test program holds galoot code from one unit with one mode.

## Findings

No blocker.

- **M1 (major, not blocking), `CMakePresets.json` (gcc-asan, clang-asan, clang-release), `test/bench/CMakeLists.txt:34-49`.** In the merge matrix, nothing now runs the forced code under a sanitizer, and nothing runs it on Clang at an optimizing level. The forced code is what every user gets by default. Clang runs forced only at `-O0` (clang-debug), where inlining changes the least. The structure tests compile forced code at `-O2` but never run it. In the three OFF presets `rga3.reference_kernels` and `rga3.reference_kernels_unforced` compile to the same program, which I checked in the OFF tree's compile commands (both get `-DGALOOT_FORCE_INLINE=0`). So the twin adds nothing where the mode is already 0, and no forced twin exists there. Failure scenario: a defect that shows only once the operations are inlined, such as an ASan or UBSan report on a temporary's lifetime or alignment inside an inlined kernel, or a Clang `-O2` miscompile of the straight-line code, reaches users in the default configuration while every preset passes. A fix that costs little: give the reference-kernel test a forced twin that fixes mode 1 by taking the core's include directories without linking `galoot::core`'s definitions, as `core_force_inline_default` does. It then runs forced in every preset, at about one second of compile time. Decision 0244's consequence says the suites in those presets "check values with the compiler's own inlining" but does not name this loss, and the owner's ruling did not weigh it as far as the records show.
- **M2 (major, not blocking), `CMakePresets.json:197-224`.** clang-measure is now OFF and clang-measure-o3 is ON, so the pair that decision 0020 set up to compare `-O2` with `-O3` on the generated kernels now differs in two settings. gcc-measure and clang-measure, the two benchmark presets, also now differ in the mode. Failure scenario: a benchmark or code-reading comparison of clang-measure against clang-measure-o3, or against gcc-measure, puts the effect of the forced inlining down to `-O3` or to the compiler. Also, a reader who follows P4 ("at the optimization level users build with") in clang-measure reads code a user does not get by default. The display name and decision 0244's consequence warn about clang-measure alone, not about the pairs. clang-measure-o3 also still builds the identity units forced, at the cost gate 2 measured for clang-measure (about 666 s, inferred from clang-measure's figures and not run). The ruling as recorded speaks of "Clang's optimized presets", and clang-measure-o3 is one. Options: (a) set clang-measure-o3 OFF too, so the pair differs only in level, and read forced code with `-DGALOOT_FORCE_INLINE=ON`; (b) keep it and state the confound in the preset's display name and in decision 0244. Recommended: (a).
- **m1 (minor), `assert.hpp:37`, `docs/guide/core.md:1044-1045`.** `-DGALOOT_FORCE_INLINE=ON` (or `OFF`, `yes`, any identifier) silently gives mode 0. For `ON`, that is the opposite of what the user asked for, and the CMake option's own ON/OFF spelling invites it. An empty value gives the preprocessor's error, not the literal message. The guide's "Any other value stops the compile with ..." is therefore false. Failure scenario: a user adds `-DGALOOT_FORCE_INLINE=ON` to make sure forcing is on, and gets every operation as a call at `-O2` with no warning. Fix: the token-pasting check above (four macro lines, tested here on both compilers), plus a compile-fail test for `ON`; or correct the guide's sentence. Recommended: the check, before release.
- **m2 (minor), `CMakeLists.txt:105-109`.** The cache option is not validated, unlike `GALOOT_CHECKING` (`MATCHES "^(ON|OFF)$"`). `-DGALOOT_FORCE_INLINE=2` or `=foo` reads as ON through `$<BOOL:...>`, with no message. The presets that keep the default do not state it, which sits uneasily with C8 ("declared rather than left to defaults"). The comment's reason, "it changes no value a test checks", is not quite true either: `core.force_inline_build` checks a value that depends on it. Failure scenario: a typo in a configure argument silently gives the forced build, which costs hours in a sanitizer tree. Fix: validate as `GALOOT_CHECKING` does. Optionally declare `"GALOOT_FORCE_INLINE": "ON"` in the other presets, so each one states its mode.
- **m3 (minor), plan 0040 section 18.2 item 3 (line 305).** The plan says `core.smoke` checks that the build's mode reaches the code. The unit did this with `core.force_inline_build`, and `core.smoke` is unchanged. Equivalent in effect, but the departure is not stated (C20) and the plan still reads as before.
- **m4 (minor), `README.md:92-97`, `assert.hpp:20-30`.** Only the guide warns against mixing modes across units. A user who reads only the README may set `-DGALOOT_FORCE_INLINE=0` on one target of a program, as Galoot's own build does for single-unit test programs. In practice that links and gives the same values (probe above), but the program breaks the one-definition rule, and under LTO which definition wins is not specified. Add one sentence to the README, and say "must" rather than "should" in the guide.
- **m5 (minor), `docs/agent/records/mutations/0040-pre-release-core-pass/README.md`, `opt-out.toml`.** The record says the presets' opt-out is not mutated because `core.force_inline_build` "checks it in each tree where it runs". In the trees where the mutants ran (ON trees), losing the CMake definition cannot be caught. Add a sentence saying so, or run one mutant of `CMakeLists.txt:109` on an OFF tree (cheap: the five targets of the selection).
- **m6 (minor, plausible), `docs/agent/records/performance/runs.tsv`.** At `81c923136055` a `convention-trace` row exits 1 and the next, 0.1 s later, exits 0, with no change between them that the log shows. If it was a mistyped command, say so; P10 forbids rerunning a check to get a pass, and the record does not show which this was. The final selection, the lint fix and the format check ran on `81c923136055-dirty`. My reruns at `048aac5` cover them.
- **Note (owner record), decision 0245.** Plan 0040 section 18 and decision 0244 item 16 cite "the owner's ruling on the gate 2 result (decision 0245 item 1, reopened), recommendation (a)". Decision 0245 on `develop` still ends "A new ruling from the owner is needed before any change under `include/`", and no record in the branch or on `develop` states the ruling.
