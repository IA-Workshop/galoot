**The merged overloads (item 1 of the brief).** `sums.cpp` includes `galoot/core.hpp`, so the products, both mismatch catch-alls, and the scalar catch-alls are all in scope. It also calls through a `using namespace galoot::core;` scope. It asserts the following on both compilers against HEAD, and against `1f52129` too, except for the two new `sum_layout` equalities:

- `L + L`, `L - L`, `M + M`, `OtherLine + OtherLine`, and `(L + M) + (L + M)` keep their type.
- A layout declared twice with the same text is the same type, and its sum is `L`.
- `const L&` plus `L&&`, and `L&` minus `const L&&`, give `L`.
- A class derived from `Line` plus itself or plus `Line` gives `Line`, and a derived line plus a derived motor gives `decltype(L{} + M{})`.
- `L + M`, `M + L`, `M - L`, and the derived pair have one type, so the layout is commutative. So do `L + OtherLine` against `OtherLine + L`, and `L + PermLine` against `PermLine + L`. A permuted layout's sum with L is the canonical set, not `L`.
- `L + Line<float>`, `L - LineO` (another algebra tag), and `M + Line<float>` still reach the catch-alls and keep the first type.
- `L + double`, `double + L`, and `L + int` remain invalid.
- `sum_layout<int, line_layout, line_layout>` is rejected, so the primary template's `metric_like` covers the one-layout form, as the standard requires for the template-id.

The printed output of 19 sums and differences, as raw bit patterns, is identical across all four builds (two header sets times two compilers): md5 `549318c2…`. It covers signed zeros on blades both operands hold and on blades one alone holds, the line with the motor in both orders, the reoriented line, and derived operands. Signed-zero and orientation behavior is unchanged, as expected, because the same-type path is still `detail::sum<±1, A>`.

## 3. Findings, most severe first

None blocks the merge.

### D1. The three zero-divisor constant-evaluation assertions do not test the check their contract names. Low; does not block (test text; cheap).

`test/core/linear_test.cpp:742-744` and `:749`; the contract above the test case (`:722-729`).

The contract reads "the check that an integer divisor is not zero ... checks every integer type, so a division by zero over std::int64_t, unsigned, or short is not a constant expression". But a built-in integer division by zero is never a constant expression, check or no check. With the `GALOOT_ASSERT` removed entirely (mutant `divide_zero_check_removed`), `linear_test.cpp` builds and `core.linear` passes on both compilers. The mutant is killed only by `core.linear_divide_consteval_zero` (`std::int64_t`, which requires `assertion_failed`) and by the three run-time `rejects_*_zero` tests. The signed-only mutant is likewise killed only by the run-time test, as the mutation README states. These lines can fail only if `operator/` stops dividing, so they are not useless (V2). But they state a property they do not fix, and a reader could take them for the evidence that unsigned and short constant evaluations hit the check. Fix: either word the contract as what the language does ("a division by zero is not a constant expression for any of the three types"), or replace the three lines with compile-fail tests for unsigned and short that require `assertion_failed`, as `linear_divide_consteval_zero` does for `std::int64_t`. I suggested such "constant-evaluation probes" in F1 myself. They were the wrong instrument for the check.

### D2. Four claims in the comments added by `a376ba8` are wrong or too broad. Low; does not block (comments only; cheap, and cheaper before release).

Each was probed on g++ 16.2.1 and clang++ 23.1.4 (`probes/claims.cpp` cases 1 to 14, `probes/big.cpp`).

- (a) `include/galoot/core/linear.hpp:348-350`: "over a signed integer type, min() / -1 overflows, which is undefined at run time and fails a constant evaluation". This is false for `short` and `signed char`. Integer promotion makes `-32768 / -1` an `int`, 32768, and the `static_cast` back is well defined (modular) since C++20. `constexpr Line<short> r = Line<short>{min, ...} / short{-1};` is a constant expression on both compilers, and its coefficient is `min()` again (cases 4 and 5). The claim holds for `std::int64_t` (case 3: GCC "overflow in constant expression", Clang "outside the range of representable values"), and for `int`, `long`, and `long long`. Suggested: "over a signed integer type at least as wide as int".
- (b) `linear.hpp:345-348`: "in a constant evaluation a division by zero of any type is not a constant expression". This is true for float and double (cases 1 and 11; GCC "'(1.0e+0 / 0.0)' is not a constant expression", Clang "division by zero"). It is false in general:
  - A user scalar whose `/` defines division by zero, here returning zero, divides by zero in a constant evaluation on both compilers (case 2).
  - GCC accepts `constexpr Line<std::complex<double>> r = x / std::complex<double>{};` (case 10 builds), while Clang rejects it.

  Suggested: "in a constant evaluation a division of a built-in floating type by zero is not a constant expression".
- (c) `include/galoot/core/mv.hpp:1051-1053`: "unless a variable or other non-template named part is in scope". A variable (case 7) and a class (case 9) named `part` do stop `part<Line>(motor)` on both compilers. A non-template function named `part` in scope does not: by C++20's rule for an unqualified name followed by `<` (P0846), lookup that finds a function makes the name a template name, so the call compiles and argument-dependent lookup finds `galoot::core::part` (case 8 builds on both). Suggested: "unless a variable or a type named part is in scope".
- (d) `linear.hpp:341-344`, the rule of the zero check: "(is_specialized and is_integer, with is_signed, digits, min(), and max()) and which has ==". `detail::integer_limits` (`mv.hpp:688-695`) also requires `min()` to convert implicitly to `std::int64_t` and `max()` to `std::uint64_t`. Consider an integer class whose limits are complete (is_specialized, is_integer, is_signed, digits, min, max) and which has `==`, but whose `min()` and `max()` return the class itself with only an explicit conversion. This is the usual shape of a big-integer or wide fixed-width class. Such a type is silently not checked: `big.cpp` divides by zero at run time in a checking build on both compilers, and the scalar's own `/` is reached. This is the residue of F1's fourth bullet, the hidden rule (C8). Suggested: add "whose min() and max() convert to std::int64_t and std::uint64_t", or drop the conversions from the concept.

Verified as stated: `truncate`'s and `part`'s rejections stop a requires-expression with their message (case 6 for `truncate`, the test for `part`); a requires-expression answers no for `x / s` over a scalar without `/` (the test, both compilers); and the check covers `__int128`, `unsigned char`, `long long`, `unsigned`, and `short` at run time, aborting with the message (cases 12 to 14 and the tests). Only `part`'s probe behavior has a test. `truncate`'s comment makes the same claim untested, which is acceptable because the two overloads share their form.
