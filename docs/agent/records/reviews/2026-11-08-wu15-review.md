## Usability checklist

The three tasks, from the examples alone: print a model value, print it with a precision, and print it under a tag's own names. All three work from the `///` comment and the README, without reading the implementation. The items are met, with these exceptions:
- the GCC context lines still spell layouts by masks, which is known and pinned only on the first line;
- the rga3 tag declares no `names`, so model lines print as `-e14`. This is the hci reading's S2, for the owner;
- the four catch-alls make probes answer yes (`is_constructible`, `requires { x + 1.0; }`, `std::formattable`). Each `///` comment states this.

**Before release (Hyrum's law):** the tag member `names` and its syntax, `std::formattable` answering yes for every scalar, the S1 widening, the rga3 printed names (S2), and the eleven literal texts.

## Findings, most severe first

No finding blocks the merge.

- **L1 (low, confirmed): `number_operand`'s reach beyond arithmetic types is untested.** `linear.hpp:286` constrains a number by `ring_scalar`, and its comment at `:291` says "a number s of any ring scalar type", but every `linear_*_number_*` source uses `double` or `int`. With `ring_scalar<S>` replaced by `std::is_arithmetic_v<S>`, the build and every `core.linear*` test pass. In that case `x + std::complex<double>{1}` or `x + rational{1}` would silently go back to the compiler's no-match error. At the tip both give the one message (probed). Fix: one compile-fail source with a non-arithmetic ring scalar.
- **L2 (low, confirmed): the spec-skipping branch of `parse` for a scalar without a formatter is untested** (`format.hpp:199-203`). If it returned `context.begin()`, every test would still pass, because all three no-formatter sources use `"{}"`. At the tip, `std::format("{:.2f}", x)` gives one error with the message (probed). Fix: a `format_scalar_without_formatter_spec` case.
- **L3 (low, confirmed): `misuse-catalogue.md` is stale after decision 0211.** Its "Graded signature" row quotes the superseded `blades` text, "holds its metric as static constexpr value", and the header now says "in a static constexpr member named value". It also states "Result at `17c9baa`" and the line numbers `blade_set.hpp:85/87`, while the scan now gives `:86/:88`, at `ac2366c`. The record that the owner ratified no longer quotes the header. Fix: a records-only edit.
- **L4 (low, confirmed): a scalar with an enabled but broken formatter gets the compiler's errors**, not silent output. The first GCC line names `std::conditional_t<true, std::formatter<num, char>, galoot::core::detail::no_scalar_formatter>`, and the formatter with no members gives 4 errors. These are user defects outside the catalogue. A named member alias would keep `detail::` off that line. Optional.
- **L5 (low, plausible): `format_test.cpp` pins a library detail in a `static_assert`.** The line is `static_assert(!std::formattable<ratio, char>)`, a fact about libstdc++'s iterator that its own comment acknowledges. A standard library whose `formattable` iterator is `format_context`'s would stop the whole test program from compiling. Fix: make it a `CHECK`, or drop it.
- **I1 (information):** `wu15-messages.md`'s "after" table predates the rewordings and omits the two new `blades` sources. The counts made here supersede it: one error each, on both compilers.
