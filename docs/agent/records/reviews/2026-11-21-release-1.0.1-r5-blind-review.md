## Usability of the README's install text and the CHANGELOG

Tasks, as a user: (1) bring Galoot into a project without a build system; (2) bring it in with `FetchContent` from the public repository; (3) find out what changed since the release I use.

- Task 2 works as copied (item 2), apart from the 1.0.1 tag, which is not on the remote yet. The block names the real URL and a pinned tag and says what `GIT_SHALLOW TRUE` buys. It is the idiom to copy.
- Task 1 reads correctly, with a worked path (`third_party/galoot`, `-I third_party`); one sentence is awkward (n3).
- Task 3: the CHANGELOG answers it, newest first, with the lead line "No public name is added, removed, or changed", which is what an upgrader wants first. The README does not mention the CHANGELOG, so a reader who arrives by the README has to find the file by looking at the repository root (n4).

## Findings

None blocking and none major.

**Minor**

- **m1. CHANGELOG.md, Build section: "the Clang optimized builds of the tests take about a fifth of the time they took" is true only of the two measurement builds.** The merge gate's record (`2026-11-21-cost-cleanup-1-0-1-matrix.md`, rows for `clang-release`, `clang-measure`, `clang-measure-o3`) has `clang-release` going from 113.7 s to 100.8 s, an 11% change, while `clang-measure` went from 667.4 s to 120.2 s and `clang-measure-o3` from 666.6 s to 127.6 s. A user who builds Galoot's tests with a Clang release build and reads the entry will expect a fivefold gain. Failure scenario: the reader's `clang-release` build takes about 100 s, and the entry reads as wrong. Suggested text: "the two Clang measurement builds of the tests take about a fifth of the time". The same gate record says the total compile work rose by 0.7% to 10.4% on nine of eleven presets; the entry does not claim otherwise ("smaller pieces", with figures for the largest compile), so I do not count that. Fixing m1 edits `CHANGELOG.md`, which is outside `docs/agent/` (open item 1). Confirmed from the record's rows; I did not remeasure.
- **m2. CHANGELOG.md, the 1.0.1 date `2026-11-21`, will not be the tag's date.** The release procedure puts the matrix, records, audit, owner walkthrough and close-out between R5 and the tag, so the date written here is the day the entry was written. The 1.0.0 entry's date equals its tag's (2026-11-15); the 1.0.1 entry is the first to differ. Failure scenario: the tag is made on a later day, and the changelog and the tag disagree for every reader. It is a date, not a statement about the code, so the risk is small. Options are in open item 1.
- **m3. `catalogue/scan-output.md` (header paragraph) and `misuse-catalogue.md` ("Regenerated on 2026-11-21" and "Result at `550e6ea`") say that the 1.0.1 work added the message `GALOOT_FORCE_INLINE must be 0 or 1`. It did not.** The message, its three compile-fail tests and the `#error` were added on 2026-11-11 (commits `2d292ef`, `d648ba2`, `3db3ce1`, `511323a`), which are in release 1.0.0; the scan was last generated at `ebe7336`, before them, so release 1.0.0 shipped with a catalogue that lacked the row. The author's own commit message for `12ab75b` says exactly this ("last generated at `ebe7336`, before the message was added"), so the commit and the records disagree. The numbers and the row are right; the attribution is wrong. Records only; edit under `docs/agent/`. The 1.0.1 release record should say that 1.0.0's catalogue was stale by one message, since the 1.0.0 record claims DoD-19 was met.

**Nits**

- **n1. CHANGELOG.md, Headers, third bullet: "Two local names ... and three more in `core/metric.hpp` and the rga3 preset".** The diff renames seven or more things: `l`, `m` (twice in different headers' sense), `m` to `result` in three functions, `m` to `form`, and a parameter `l` to `axis` on four overloads. The count "three more" cannot be reproduced from the diff, and "local names" is not exact for `axis`, which is the parameter of a public function (its `///` comment changed too). The next sentence, that a parameter's name is not part of a C++ interface, covers the point. Suggest dropping the count: "Some local names and a parameter name in ...".
- **n2. CHANGELOG.md, lead sentence: "a program that compiled with 1.0.0 compiles with 1.0.1."** True of a program that uses the public interface. A program that called `galoot::core::detail::apply` without a target layout (the tests did) no longer compiles; the entry says "Nothing in `detail` is public" below. Suggest "a program that uses only Galoot's public names".
- **n3. README.md lines 38 to 40: "Copy or vendor the `include/galoot` directory, keeping its name, `galoot`, into a directory on your include path".** The participle phrase dangles. Suggest: "Copy the `include/galoot` directory, keeping the name `galoot`, into a directory on your include path." The worked example after it is clear. This sentence came in with the header-hygiene merge, not with R5, and ships in R.
- **n4. README.md does not point to CHANGELOG.md.** A user upgrading from 1.0.0 who reads only the README learns the version and the tag but not where the changes are. One line under "Using Galoot" or next to the licence would do. Not required by plan 4.4 or decision 0252 item 15.
