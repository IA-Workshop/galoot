## What each outcome says

1. Cases 8 and 17, implicit conversions (the first run's case 17 was a point into a motor, which is lossy; the corrected case is a line). Every conversion between layouts is an `explicit` constructor (STYLE S8), so an implicit one reaches no constructor and stays the compiler's error, as decision 0155 item 2 rules. The texts grew: GCC adds "note: explicit conversion function was not considered", pointing at the declaration of the conversion's catch-all (whose message is on the next lines, which GCC does not show), and Clang's notes list the new candidate constructors (28 lines against 16). The WU8a record's sentence that this row would be "replaced with the conversion catch-all" does not hold: an explicit constructor is not a candidate in copy-initialization. Measured alternative, not adopted (decision 0155 item 2 is the owner's): with the lossy catch-all declared without `explicit`, case 8 gives the conversion's own message, GCC 10 lines / 925 and Clang 9 / 268 (scratch copy of the header, selections `wu8b-diagnostics:implicit-catch-all:*` in the run log); the cost is a non-explicit single-argument constructor, against S8's wording, and `std::is_convertible_v<Motor, Point>` answering yes.
2. Case 9, the explicit lossy conversion: one error with the literal on both compilers (before, GCC printed 65 lines of candidates). The longest GCC line is the instantiation context, which prints both layouts as masks.
3. Cases 10 and 22 (F7, and the review's S2): same counts, new words. A layout that full, of_grade, or a product computes is in canonical order with every sign +1, and lists no names in the user's code. For such a layout the absent message no longer points at a list the user never wrote, and the other-orientation message gives the naming rule, which is where it is the fix. A hand-written layout in canonical order gets the same messages, which are true of it too.
4. Cases 11 to 14 (F8): the scalar is now constrained in the template head by `std::destructible` only and checked in the class body in a fixed order, so each fault gives one error with its own literal. `bool` is now rejected (before it compiled; `ring_scalar<bool>` is false). Case 14's second error on GCC is the program's own use of a member of the scalar, `s.coefficients[0].sixteenths`: the storage of a rejected scalar that is not semiregular is a placeholder, so that making the value raises no second error; a use of a member of its coefficients then fails. The declaration alone gives one error on both compilers (`core.mv_scalar_without_default`).
5. Cases 15, 16, and 18 (F10, and the review's C1): one error with its own literal, instead of 65 lines of candidates on GCC (case 15), the count message, whose cause the user did not commit (case 16), or the compiler's "would use explicit constructor" (case 18). Case 19 (C4): one value of another type has its own message. Case 20 (C2): one error, where the use of the result added a second. Case 21 (S3): a move-only scalar is told to make it copyable, not to give it a default constructor.

Routes used (plan 0016, section 5): 2 (literal catch-alls), 3 (one error per mistake: the scalar's faults are reported first-only, and a single non-coefficient argument no longer reaches the count catch-all), 4 (the scalar checked in the class body under a weaker constraint), and 7 (message style).
